# 1. OSINT와 Reconnaissance(정찰)

## 1.1. OSINT와 Reconnaissance 개요

### OSINT (Open Source Intelligence)

- OSINT(Open Source Intelligence)는 뉴스, SNS, GitHub, 공식 문서 등 인터넷에 공개된 출처에서 정보를 수집하고 분석하는 것을 의미한다.
- 공개된 정보를 활용하기 때문에 대상 시스템에 직접적인 요청을 보내지 않고도 다양한 정보를 확보할 수 있다.

### Reconnaissance (Recon)

- Reconnaissance(Recon)는 군사 용어인 '정찰'에서 유래한 개념이다.
- 버그헌팅에서는 실제 공격에 앞서 대상 시스템의 정보를 수집하고, 유효한 공격 표면(Attack Surface)을 최대한 많이 확보하는 단계이다.
- 정찰 단계에서 얼마나 많은 자산과 기능을 파악하느냐에 따라 이후 취약점 탐색의 범위가 달라진다.

### 정보 수집의 두 가지 축

1. **서브도메인 열거(Subdomain Enumeration)**
   - 대상의 범위(Scope)가 넓을 때 관련 자산을 식별하는 과정이다.
   - `api.example.com`, `dev.example.com`, `staging.example.com`과 같은 서브도메인을 찾아 공격 표면을 확장한다.

2. **콘텐츠 디스커버리(Content Discovery)**
   - 식별된 웹 자산 내부에서 디렉터리, 파일, API, 기능 등을 탐색하는 과정이다.
   - 현재 웹사이트에서 직접 노출되지 않는 경로까지 확인하여 추가적인 공격 표면을 확보한다.

# 2. 핵심 정보 수집 도구 및 기술

## 2.1. 기술 식별(Web Technologist)

### Wappalyzer

- **Wappalyzer**는 웹사이트에서 사용하는 기술 스택을 분석하는 브라우저 확장 도구이다.
- CMS, JavaScript 프레임워크, 웹 서버, 분석 도구 등의 정보를 확인할 수 있다.
- 공개적으로 노출된 정보를 기반으로 분석하기 때문에 일반적인 사용에서는 대상 서버에 별도의 대량 요청을 발생시키지 않는다.

---

## 2.2. 서브도메인 열거(Subdomain Enumeration)

### Subfinder

- **Subfinder**는 다양한 공개 데이터 소스를 활용하여 서브도메인을 수집하는 패시브(Passive) 정보 수집 도구이다.
- 검색 엔진, DNS 데이터베이스, VirusTotal, Shodan 등의 공개 데이터를 활용할 수 있다.
- 대상 서버에 직접적인 스캔 요청을 보내는 방식이 아니라 공개된 정보를 수집하는 방식이므로 정찰 초기 단계에서 활용하기 좋다.

---

## 2.3. 디렉터리 및 경로 탐색(Content Discovery)

### Dirsearch

- **Dirsearch**는 사전(Dictionary)에 포함된 경로를 웹 서버에 요청하여 숨겨진 디렉터리나 파일을 탐색하는 액티브(Active) 도구이다.
- HTTP 상태 코드 등을 확인하여 유효한 경로를 판단할 수 있다.
- 대표적인 상태 코드는 다음과 같다.

| 상태 코드 | 의미 |
|---|---|
| `200` | 요청이 정상적으로 처리됨 |
| `301`, `302` | 다른 위치로 리다이렉션 |
| `403` | 접근이 거부됨 |
| `404` | 리소스를 찾을 수 없음 |

### Waybackurls

- **Waybackurls**는 Wayback Machine에 저장된 과거 URL 데이터를 활용하여 대상 도메인과 관련된 URL을 수집하는 도구이다.
- 현재는 삭제되거나 외부에서 보이지 않는 과거 엔드포인트나 파라미터를 발견하는 데 활용할 수 있다.
- 오래된 API나 개발 과정에서 사용되었던 기능이 현재 서버에 남아 있는지 확인하는 데 도움이 된다.

---

## 2.4. JavaScript 분석

### LinkFinder

- **LinkFinder**는 JavaScript 파일을 분석하여 URL, 엔드포인트 등의 정보를 추출하는 도구이다.
- 정규표현식을 활용하여 JavaScript 소스 내부에 존재하는 API 경로 등을 찾아낸다.

### JSLeak

- **JSLeak**은 JavaScript 소스에서 엔드포인트뿐만 아니라 API Key, Token, Password와 같은 민감한 정보가 노출되어 있는지 확인하는 데 활용할 수 있는 도구이다.
- 클라이언트 측에 공개된 JavaScript 코드에 민감한 정보가 포함되어 있는지 점검하는 데 유용하다.

---

## 2.5. 통합 정찰 프레임워크

### Amass

- DNS, 서브도메인, 네트워크 자산 등의 정보를 수집하여 공격 표면을 파악하는 데 활용할 수 있다.

### BBOT

### BBRF

- 버그바운티 및 보안 테스트에서 수집한 자산과 정찰 결과를 관리하고 자동화하는 데 활용할 수 있는 프레임워크이다.

# 3. 네트워크 포트 스캐닝(Nmap)

## 3.1. Nmap 개요

- **Nmap(Network Mapper)**은 네트워크 보안 감사 및 자산 탐색에 널리 사용되는 도구이다.
- 대상 시스템에서 열려 있는 포트와 실행 중인 서비스를 확인할 수 있다.
- 서비스 버전이나 운영체제 등의 정보를 확인하여 추가적인 보안 점검의 기반으로 활용할 수 있다.

---

## 3.2. 주요 옵션

| 옵션 | 설명 |
|---|---|
| `-p` | 특정 포트를 지정하여 스캔한다. |
| `-p-` | 전체 포트 범위를 스캔한다. |
| `-sV` | 실행 중인 서비스의 버전 정보를 확인한다. |
| `-O` | 대상 시스템의 운영체제를 탐지한다. |
| `-sC` | 기본 NSE 스크립트를 실행한다. |
| `-T4` | 스캔 속도를 높이는 타이밍 옵션이다. |

예를 들어 특정 포트만 확인하거나 전체 포트를 대상으로 서비스 정보를 확인하는 방식으로 활용할 수 있다.

---

## 3.3. NSE(Nmap Scripting Engine)

- **NSE(Nmap Scripting Engine)**는 Lua 언어로 작성된 스크립트를 Nmap과 함께 실행할 수 있도록 제공되는 기능이다.
- 기본적인 포트 스캔뿐만 아니라 다음과 같은 다양한 보안 진단에 활용할 수 있다.
  - 취약한 서비스 탐지
  - SSL/TLS 설정 확인
  - 서비스 정보 수집
  - 네트워크 서비스에 대한 추가적인 보안 점검

# 4. 실전 사례: 포트 스캐닝을 통한 버그헌팅

## 4.1. Andy Gill의 Pornhub 버그바운티 사례

- **상황**
  - Pornhub의 버그바운티 프로그램에 참여하여 대상 시스템을 정찰하였다.

- **접근**
  - 먼저 서브도메인을 식별한 뒤 `stage.pornhub.com`과 같은 스테이징 환경에 집중하였다.

- **발견**
  - Nmap을 이용하여 전체 포트를 스캔하고 서비스 정보를 확인하였다.
  - 그 결과 비표준 포트에서 실행 중인 서비스를 발견하였고, 해당 서비스가 **Memcached**임을 식별하였다.

- **영향**
  - Memcached가 적절한 접근 제어 없이 외부에 노출되어 있는 경우 내부 데이터가 노출될 가능성이 있다.
  - 해당 문제를 검증하여 버그바운티 포상금으로 **$2,500**를 받았다.

- **교훈**
  - 복잡한 웹 해킹 기술을 사용하지 않더라도 기본적인 포트 스캔과 서비스 식별만으로 중요한 보안 문제를 발견할 수 있다.
  - 웹 서비스의 기본 포트인 `80`, `443`만 확인하는 것이 아니라 비표준 포트에서 실행되는 서비스까지 확인하는 것이 중요하다.

# 5. 대화형 언어 모델(LLM)의 이해

## 5.1. LLM(Large Language Model)

- **LLM(Large Language Model)**은 방대한 텍스트 데이터를 학습하여 주어진 문맥에서 적절한 다음 토큰을 예측하는 대규모 언어 모델이다.
- 모델의 성능은 단순히 매개변수 개수뿐만 아니라 학습 데이터, 모델 구조, 학습 방법 등 다양한 요소의 영향을 받는다.
- 대표적인 LLM으로 GPT 계열 등의 모델이 있다.

---

## 5.2. RLHF(Reinforcement Learning from Human Feedback)

- **RLHF(Reinforcement Learning from Human Feedback)**는 인간의 피드백을 활용하여 모델이 사람의 의도에 더욱 적절하게 응답하도록 학습하는 방법이다.
- 사용자가 원하는 형태의 답변과 원하지 않는 답변에 대한 인간의 평가를 학습 과정에 반영한다.

### 비유

- LLM이 세상에 대한 지식은 많지만 사회적 상황을 충분히 이해하지 못하는 '청소년'이라면, RLHF를 거친 모델은 인간의 의도와 선호에 맞게 행동하는 방법을 학습한 '성인'에 비유할 수 있다.
- 다만 RLHF는 모델의 지식이나 지능 자체를 단순히 증가시키는 기술이라기보다는 **인간의 선호와 의도에 맞게 모델의 행동을 조정하는 과정**으로 이해하는 것이 적절하다.

# 7. AI의 보안 위협: 프롬프트 인젝션

## 7.1. Prompt Injection 개념

- **프롬프트 인젝션(Prompt Injection)**은 공격자가 특정한 지시를 입력하여 AI 시스템의 의도된 동작과 다른 결과를 유도하는 공격 기법이다.
- AI 시스템에 내부 데이터나 민감한 정보가 연결되어 있는 경우, 잘못된 설계로 인해 정보가 노출될 가능성이 있다.

---

## 7.2. 실습 사례: Gandalf

- **Gandalf**는 Lakera에서 제공하는 프롬프트 인젝션 학습용 실습 환경이다.
- 사용자가 직접 다양한 프롬프트를 입력하면서 AI의 방어 체계를 우회하려는 시도를 실습할 수 있다.
- 이 과정에서 단순한 직접 질문뿐만 아니라 문맥 변경, 역할극 등의 방식으로 모델의 응답을 유도할 수 있다는 점을 확인할 수 있다.

### 시사점

- AI 시스템을 보안적으로 신뢰하기 위해서는 모델의 응답뿐만 아니라 애플리케이션의 입력 검증, 권한 관리, 데이터 접근 제어 등이 함께 고려되어야 한다.
- 특히 기업의 내부 정보나 개인정보 등을 AI 서비스에 입력할 때는 데이터 처리 정책과 보안 설정을 확인해야 한다.

# 9. ChatGPT를 활용한 취약점 분석 실습

## 9.1. 사례 1: Hugging Face Transformers

- **CVE-2023-2800**과 관련된 코드 분석 과정에서 `tempfile.mktemp` 함수의 사용 부분을 ChatGPT에 입력하여 분석을 요청할 수 있다.
- `mktemp`는 파일 이름을 생성하지만 실제 파일을 안전하게 생성하는 방식이 아니기 때문에, 파일 이름을 생성한 이후 실제 파일을 사용하는 사이에 공격자가 개입할 수 있는 **레이스 컨디션(Race Condition)** 문제가 발생할 가능성이 있다.
- 안전한 임시 파일 생성을 위해서는 상황에 맞는 안전한 임시 파일 생성 함수를 사용하는 것이 필요하다.

---

## 9.2. 사례 2: Draw.io Proxy

- 리다이렉션을 처리하는 코드의 로직을 ChatGPT에 입력하여 보안 문제를 분석할 수 있다.
- 리다이렉션된 URL이 현재 호스트와 동일한지 적절하게 검증하지 않는 경우, 특정 조건에서 반복적인 리다이렉션으로 인해 **서비스 거부(DoS)**가 발생할 가능성을 확인할 수 있다.
- 이처럼 AI를 활용하면 복잡한 코드의 흐름을 분석하고 논리적 결함을 빠르게 찾는 데 도움을 받을 수 있다.

# 10. ChatGPT를 활용한 PoC 코드 생성

## 10.1. Python PoC 생성

- Burp Suite에서 확인한 HTTP 요청을 기반으로 Python의 `requests` 라이브러리를 사용하는 PoC 형태로 변환할 수 있다.
- 요청에 포함된 헤더, 쿠키, 파라미터 등의 구조를 분석하여 재현 코드의 형태로 정리하는 데 활용할 수 있다.
- 이를 통해 취약점 재현 및 제보에 필요한 시간을 단축할 수 있다.

## 10.2. Fetch API PoC 생성

- 브라우저 개발자 도구의 콘솔에서 실행할 수 있는 **Fetch API** 형태로 HTTP 요청을 변환할 수도 있다.
- 별도의 프로그램을 설치하지 않고 브라우저 환경에서 요청을 재현할 수 있다는 장점이 있다.
- 다만 실제 취약점 검증은 반드시 허가된 테스트 환경이나 버그바운티의 허용 범위 내에서 수행해야 한다.

# 12. 좋은 버그 리포트 작성 전략

## 12.1. 실수 방지

### 범위(Scope) 확인

- 버그바운티 프로그램에 참여하기 전에 반드시 허용된 대상과 제외 대상을 확인해야 한다.
- 인수합병, 서비스 변경 등의 이유로 일시적으로 테스트가 금지되는 **블랙아웃 기간**이 존재할 수도 있으므로 프로그램 정책을 확인해야 한다.

### 타겟 식별

- 웹사이트의 로고나 서비스 이름만 보고 소유권을 판단해서는 안 된다.
- DNS, WHOIS, 공식 문서 등의 정보를 활용하여 실제 대상 자산인지 확인해야 한다.

### 자동화 도구 결과 검증

- 자동화 도구가 SQL Injection이나 SSL 설정 문제 등을 탐지했다고 해서 바로 취약점으로 판단해서는 안 된다.
- 오탐(False Positive)이 발생할 수 있으므로 수동으로 결과를 검증해야 한다.

### 동영상 제보

- 동영상은 필요한 경우에만 첨부하는 것이 좋다.
- 첨부할 경우 불필요한 과정은 제거하고 핵심적인 재현 과정이 명확하게 보이도록 작성한다.

# 13. 공격 시나리오(Attack Scenario) 작성

좋은 취약점 리포트에서는 단순히 취약점의 존재만 설명하는 것이 아니라 공격자가 해당 취약점을 어떻게 활용할 수 있는지를 설명해야 한다.

## 13.1. 공격 시나리오의 3요소

1. **공격자의 의도**
   - 공격자가 무엇을 얻거나 수행하려는지 설명한다.

2. **공격 결과 및 이익**
   - 취약점을 통해 공격자가 얻을 수 있는 정보나 권한을 설명한다.

3. **공격 방식**
   - 어떤 조건과 절차를 통해 취약점이 발생하는지 설명한다.

## 13.2. 시나리오 작성 시 고려사항

- 공격자의 초기 권한
- 피해자의 존재 여부
- 필요한 전제 조건
- 공격 과정
- 최종적인 영향(Impact)

위 내용을 단계적으로 작성하면 제보자가 발견한 취약점의 위험성을 더욱 명확하게 전달할 수 있다.

# 14. Markdown 활용법

## 14.1. Markdown 개요

- **Markdown**은 일반 텍스트에 간단한 문법을 추가하여 문서를 구조화할 수 있는 경량 마크업 언어이다.
- GitHub, 기술 문서, 프로젝트 README 등 다양한 플랫폼에서 사용된다.

## 14.2. 주요 문법

### 헤더

```markdown
# 제목 1
## 제목 2
### 제목 3
```

### 강조

```markdown
*이탤릭*

**볼드체**
```

### 코드 블록

````markdown
```bash
명령어
```
`````

### 인용

```markdown
> 참고 자료나 이전 리포트의 내용을 인용한다.
```

### 테이블

```markdown
| 항목 | 설명 |
|---|---|
| A | 내용 |
| B | 내용 |
```

Markdown을 적절하게 활용하면 기술적인 내용을 계층적으로 정리하고 명령어, 코드, 참고 자료 등을 가독성 있게 표현할 수 있다.

# 15. 핵심내용 (Summary)

1. **Recon의 중요성**

   * 정찰은 대상의 공격 표면(Attack Surface)을 최대한 넓게 파악하는 과정이며, 버그헌팅의 기초가 된다.

2. **패시브와 액티브 정보 수집**

   * Subfinder, Waybackurls 등의 패시브 정보 수집으로 대상의 정보를 확보한 뒤 Dirsearch, Nmap 등의 액티브 도구를 이용하여 실제 자산과 서비스를 확인할 수 있다.

3. **다양한 공격 표면 탐색**

   * 웹사이트의 `80`, `443` 포트뿐만 아니라 비표준 포트에서 실행되는 서비스까지 확인해야 한다.
   * Nmap을 이용한 서비스 식별은 예상하지 못했던 공격 표면을 발견하는 데 도움이 된다.

4. **과거 데이터의 활용**

   * Wayback Machine에 저장된 과거 URL이나 JavaScript 소스에서 발견되는 오래된 엔드포인트는 현재 웹사이트에서 보이지 않는 공격 표면을 파악하는 데 활용할 수 있다.

5. **AI의 활용**

   * LLM은 코드 분석, 취약점 원리 분석, HTTP 요청 분석, PoC 작성, 보고서 작성 등의 작업을 보조할 수 있다.

6. **AI 결과의 검증**

   * AI가 제시한 취약점이나 분석 결과를 그대로 신뢰해서는 안 된다.
   * 자동화 도구와 마찬가지로 직접 코드를 검토하고 재현 가능성을 확인하여 오탐 여부를 검증해야 한다.

7. **AI 자체의 보안 문제**

   * 프롬프트 인젝션과 같은 공격을 통해 AI의 의도하지 않은 동작이 발생할 수 있다.
   * AI에 민감한 데이터를 입력할 때는 데이터 처리 및 정보 유출 가능성을 고려해야 한다.

8. **좋은 버그 리포트**

   * 명확한 타겟 식별, 재현 가능한 과정, 기술적인 원인, 공격 시나리오, 영향(Impact)을 포함해야 한다.
   * 특히 취약점으로 인해 공격자가 실제로 무엇을 얻을 수 있는지를 명확하게 설명하는 것이 중요하다.

9. **AI의 역할**

   * AI는 버그헌터를 대체하는 도구라기보다는 반복적인 분석과 문서 작업을 줄이고, 취약점 분석과 문제 해결을 보조하는 **Assistant** 역할로 활용하는 것이 적절하다.
