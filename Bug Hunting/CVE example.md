# 1. CVE-2017-1000486 취약점 개요 및 CVSS 분석

## 1.1. 취약점 정보

CVE-2017-1000486은 **PrimeFaces 5.x**에서 발생하는 원격 코드 실행(RCE) 취약점이다.

공격자가 조작된 데이터를 서버에 전달하면 서버 측에서 악성 EL(Expression Language)이 처리될 수 있으며, 특정 조건에서 원격 코드 실행으로 이어질 수 있다.

## 1.2. CVSS 분석

해당 취약점은 CVSS 9.8(Critical)로 평가된다.

- **공격 벡터(Network):** 네트워크를 통해 원격에서 공격할 수 있다.
- **권한 요구(None):** 특정 조건에서는 인증 없이 공격이 가능하다.
- **사용자 상호작용(None):** 피해자의 별도 클릭이나 동작이 필요하지 않다.
- **기밀성 영향(High):** 서버의 중요 정보가 노출될 수 있다.
- **무결성 영향(High):** 서버의 데이터나 시스템이 변경될 수 있다.
- **가용성 영향(High):** 시스템의 정상적인 서비스 제공이 중단될 수 있다.

따라서 공격이 성공할 경우 서버에 심각한 영향을 미칠 수 있는 **Critical 등급의 취약점**이다.

# 2. 취약점 발생 원리

## 2.1. PBE (Password Based Encryption)

PBE(Password Based Encryption)는 패스워드를 기반으로 암호화 키를 생성하는 방식이다.

PrimeFaces는 데이터를 보호하기 위해 PBE 기반의 암호화 방식을 사용했다.

## 2.2. 기본 암호화 설정 노출

PrimeFaces의 오픈소스 코드에서 암호화에 사용되는 기본 패스워드와 Salt, Iterations 등의 설정값을 확인할 수 있었다.

암호화에 사용되는 비밀값이 안전하게 관리되지 않고 소스코드에 노출되어 있으면 공격자가 이를 이용하여 서버가 신뢰할 수 있는 형태의 데이터를 생성할 가능성이 발생한다.

따라서 데이터를 암호화하는 것뿐만 아니라 **암호화 키와 관련된 비밀값을 안전하게 관리하는 것이 중요하다.**

## 2.3. EL (Expression Language)

EL(Expression Language)은 Java 기반 웹 애플리케이션에서 객체나 속성 등에 접근하기 위해 사용하는 표현식 언어이다.

일반적으로 다음과 같은 형태로 사용한다.

```text
#{...}
```

취약한 처리 과정에서는 공격자가 조작한 데이터를 통해 악성 EL 표현식을 전달할 수 있으며, 서버가 이를 적절하게 검증하지 않고 처리하면 의도하지 않은 객체 접근이나 코드 실행으로 이어질 수 있다.

# 3. Python PoC를 이용한 취약점 검증

## 3.1. PoC 분석

공개된 Python PoC를 분석하여 PrimeFaces 취약점의 동작 원리를 확인한다.

PoC는 PrimeFaces의 암호화 방식을 이용하여 서버가 처리할 수 있는 형태의 데이터를 생성하고 이를 서버에 전달하는 방식으로 동작한다.

실습에서는 `whoami`와 같은 명령을 이용하여 서버 측에서 명령 실행이 가능한지 확인했다.

## 3.2. 실행 결과

실습 환경에서 PoC 실행 결과 다음과 같은 응답을 확인했다.

```text
root
```

이를 통해 해당 실습 환경에서 서버 측 명령 실행이 가능함을 확인했다.

# 4. Metasploit 외부 모듈 로드 및 트러블슈팅

## 4.1. 외부 모듈 확보

Metasploit 데이터베이스에 필요한 모듈이 존재하지 않는 경우 Searchsploit을 이용하여 Exploit-DB에 등록된 관련 Ruby(`.rb`) 스크립트를 확인할 수 있다.

공개된 Exploit을 사용할 때에는 코드의 동작과 대상 버전을 먼저 확인하고, 본인이 통제하는 실습 환경에서만 검증해야 한다.

## 4.2. 외부 모듈 로드 에러 해결

다운로드한 Ruby 스크립트를 직접 실행하면 Metasploit에서 사용하는 `Msf` 관련 상수를 찾지 못해 오류가 발생할 수 있다.

이 경우 스크립트를 Metasploit의 사용자 모듈 경로에 배치한 뒤 `msfconsole`에서 모듈을 다시 로드한다.

```text
~/.msf4/modules/...
```

이후 다음 명령어를 실행한다.

```text
reload_all
```

이를 통해 외부에서 추가한 모듈을 Metasploit에서 인식할 수 있다.

## 4.3. 공격 실패 및 원인 분석

모듈을 정상적으로 로드한 후 실행했지만 다음과 같은 메시지가 출력되며 실패할 수 있다.

```text
Server is not vulnerable
```

이러한 경우 단순히 모듈의 문제라고 판단하지 않고 실제로 서버에 어떤 HTTP 요청이 전달되었는지 확인하는 과정이 필요하다.

## 4.4. Burp Suite를 이용한 패킷 분석

Metasploit의 `PROXIES` 옵션을 설정하여 Burp Suite를 중간 프록시로 연결하면 실제 HTTP 요청과 응답을 확인할 수 있다.

이를 통해 다음과 같은 항목을 분석할 수 있다.

- HTTP 메서드
- 요청 URL
- 요청 헤더
- 파라미터
- 페이로드
- URL 인코딩 상태
- 서버 응답

실습 환경에 따라 프록시와 관련된 설정을 추가해야 할 수 있으며, 수업에서는 `ReverseAllowProxy true` 설정을 함께 사용했다.

## 4.5. 인코딩 문제 분석

패킷을 분석한 결과 Metasploit 모듈에서 생성한 페이로드의 인코딩 방식이 서버가 기대하는 형태와 일치하지 않는 문제가 발생했다.

특히 **Double URL Encoding**이 적용되면서 서버가 페이로드를 정상적으로 해석하지 못하는 상황이 발생할 수 있다.

따라서 다음과 같은 과정을 통해 문제를 분석한다.

1. Burp Suite에서 실제 전송되는 HTTP 요청을 확인한다.
2. 요청 데이터의 인코딩 상태를 분석한다.
3. 서버가 기대하는 형식과 비교한다.
4. 필요한 경우 테스트 스크립트나 모듈의 인코딩 처리 방식을 수정한다.
5. 수정된 데이터를 실습 환경에서 다시 검증한다.

수정 후 실습 환경에서 서버 측 명령 실행이 정상적으로 이루어지는 것을 확인했다.

# 5. Apache Superset 취약점 분석

## 5.1. CVE-2023-27524 개요

CVE-2023-27524는 **Apache Superset**에서 발생하는 보안 취약점으로, 기본값으로 설정된 `SECRET_KEY`가 사용되는 환경에서 세션의 신뢰성을 훼손할 수 있다.

## 5.2. 세션 구조와 문제점

Apache Superset은 Python Flask 기반의 웹 애플리케이션으로, 세션 정보를 클라이언트 측 쿠키에 저장하는 구조를 사용할 수 있다.

일반적인 세션 쿠키는 다음과 같은 특징을 가진다.

- 클라이언트가 쿠키 데이터를 보유한다.
- 쿠키 내부의 데이터 자체는 사용자가 확인할 수 있다.
- 서버는 서명을 이용하여 쿠키가 정상적으로 생성되었는지 검증한다.
- 서명에 사용되는 비밀 키가 안전하게 관리되어야 한다.

그러나 `SECRET_KEY`가 기본값으로 설정되어 있으면 해당 키가 외부에 알려진 상황에서 공격자가 세션의 신뢰성을 훼손할 가능성이 발생한다.

## 5.3. 공격 시나리오

취약한 실습 환경에서는 다음과 같은 흐름으로 취약점을 검증할 수 있다.

1. **Secret Key 확인:** 공개된 소스코드나 문서 등을 통해 기본 Secret Key가 사용되고 있는지 확인한다.
2. **세션 위조 가능성 분석:** 세션 서명에 사용되는 키를 이용하여 세션 검증 과정의 취약성을 확인한다.
3. **권한 상승 검증:** 실습 환경에서 조작된 세션이 관리자 권한으로 처리되는지 확인한다.
4. **인증 우회 확인:** 서버가 위조된 세션을 정상적인 관리자 세션으로 인식하는지 검증한다.

# 6. PostgreSQL을 이용한 RCE 연계

## 6.1. 취약점 체이닝

Superset에서 관리자 권한을 확보한 이후에는 애플리케이션 자체의 기능뿐만 아니라 연결된 데이터베이스의 권한과 설정까지 분석할 수 있다.

이처럼 하나의 취약점을 통해 확보한 권한을 다른 기능과 결합하여 더 큰 영향을 발생시키는 것을 **취약점 체이닝(Vulnerability Chaining)**이라고 한다.

## 6.2. PostgreSQL 관련 위험성

PostgreSQL에는 서버 환경에서 외부 프로그램과 연계할 수 있는 기능이 존재한다.

특정 권한과 설정이 충족되는 환경에서는 데이터베이스 기능이 운영체제 명령 실행으로 이어질 수 있으므로, 데이터베이스 계정의 권한과 관련 기능을 적절하게 제한해야 한다.

## 6.3. 체이닝 구조

실습에서는 다음과 같은 공격 체인의 가능성을 분석했다.

```text
기본 SECRET_KEY
        ↓
세션 위조 가능성
        ↓
Superset 관리자 권한
        ↓
데이터베이스 기능 접근
        ↓
조건 충족 시 운영체제 명령 실행
        ↓
RCE
```

이를 통해 단순한 인증 관련 취약점이 데이터베이스와 운영체제 영역까지 영향을 확대할 수 있음을 확인할 수 있다.

# 7. Azure Service Fabric 취약점 분석

## 7.1. Super FabriXss - CVE-2023-23383

CVE-2023-23383은 Microsoft Azure Service Fabric Explorer(SFX)에서 발생한 **Stored XSS 관련 취약점**이다.

URL 파라미터가 적절하게 필터링되지 않은 상태로 화면에 출력될 수 있으며, 특정 UI 동작과 결합될 경우 악성 스크립트가 실행될 수 있다.

## 7.2. 발현 조건

해당 취약점은 단순히 스크립트를 입력하는 것만으로 항상 실행되는 것은 아니다.

특정 URL을 통해 전달된 데이터가 UI에서 렌더링되는 과정과 사용자의 특정 상호작용이 결합되어 XSS가 발현될 수 있다.

따라서 웹 취약점 분석에서는 단순히 입력값이 출력되는지 여부뿐만 아니라 **실제 실행 조건과 데이터 흐름**까지 확인해야 한다.

## 7.3. 취약점 체이닝

해당 사례에서는 XSS가 다른 기능과 결합하면서 영향 범위가 확대될 수 있다.

```text
조작된 URL
    ↓
관리자의 접근
    ↓
특정 UI 상호작용
    ↓
XSS 실행
    ↓
관리자 권한으로 요청 발생
    ↓
클러스터 관리 기능 악용 가능성
    ↓
컨테이너 환경에 대한 영향
```

XSS 자체의 영향만 분석하는 것이 아니라, **피해자의 권한으로 실행되는 요청과 애플리케이션의 관리 기능을 함께 분석하는 것이 중요하다.**

# 8. 사례 1: VMware Workspace ONE Access

## 8.1. CVE-2022-22954 개요

CVE-2022-22954는 VMware Workspace ONE Access에서 발생한 **Server-Side Template Injection(SSTI) 관련 원격 코드 실행 취약점**이다.

## 8.2. 발생 원인

Workspace ONE Access는 Java 기반의 템플릿 엔진인 **FreeMarker**를 사용한다.

FreeMarker는 데이터 모델과 템플릿을 결합하여 동적으로 HTML 등의 결과물을 생성한다.

취약한 환경에서는 사용자 입력값이 템플릿 처리 과정에 적절하게 제한되지 않아 공격자가 템플릿 표현식을 주입할 가능성이 발생한다.

주요 원인은 다음과 같이 정리할 수 있다.

1. FreeMarker는 템플릿을 이용하여 동적인 결과물을 생성한다.
2. 템플릿 엔진에는 다양한 객체와 기능에 접근할 수 있는 기능이 존재한다.
3. 사용자 입력이 템플릿 처리 과정에 직접 영향을 미치면 SSTI가 발생할 수 있다.
4. 적절한 보안 설정과 입력 검증이 적용되지 않은 경우 서버 측 코드 실행으로 이어질 가능성이 발생한다.

## 8.3. 취약점의 의의

이 사례는 웹 애플리케이션에서 템플릿 엔진을 사용할 때 **사용자 입력을 신뢰해서는 안 된다는 점**을 보여준다.

특히 템플릿 표현식이 서버 측에서 실행되는 구조라면 입력값의 처리 범위와 템플릿 엔진의 권한을 제한해야 한다.

# 9. 사례 2: ImageMagick 파일 유출

## 9.1. CVE-2022-44268 개요

CVE-2022-44268은 이미지 처리 도구인 **ImageMagick**에서 발생한 파일 읽기 관련 취약점이다.

해당 취약점은 HackerOne 버그바운티에서 보고된 사례로 알려져 있으며, 이미지 처리 과정에서 특정 메타데이터가 파일 경로로 처리되는 로직을 악용하여 서버 내부 파일이 이미지에 포함될 수 있는 문제가 발생했다.

## 9.2. 공격 시나리오

실습 환경에서는 다음과 같은 흐름으로 취약점의 원리를 확인할 수 있다.

1. 이미지 업로드 기능을 분석한다.
2. 이미지 파일의 메타데이터가 처리 과정에서 어떻게 사용되는지 확인한다.
3. 특정 메타데이터가 파일 경로로 해석될 가능성을 분석한다.
4. 서버에서 처리된 이미지를 다시 다운로드한다.
5. 결과 이미지에 서버 파일의 내용이 포함되는지 확인한다.

## 9.3. Root Cause Analysis

취약점의 핵심은 이미지의 특정 메타데이터를 처리하는 과정에서 **사용자 제어 데이터가 파일 경로로 사용될 수 있었다는 점**이다.

분석 과정은 다음과 같이 정리할 수 있다.

1. **취약점 위치:** ImageMagick의 PNG 처리 과정에서 텍스트 청크를 읽는 로직을 분석한다.
2. **특정 키워드 처리:** 특정 키워드가 파일명과 관련된 값으로 처리되는 로직이 존재한다.
3. **파일 읽기:** 해당 값이 파일 경로로 처리되면서 서버 내부 파일을 읽을 가능성이 발생한다.
4. **데이터 저장:** 읽어온 데이터가 이미지의 프로필 정보에 포함될 수 있다.
5. **정보 노출:** 처리된 이미지를 다시 확인하면 서버 내부 파일의 내용이 포함될 가능성이 있다.

## 9.4. Exploit 실습 및 데이터 확인

실습에서는 처리된 이미지의 메타데이터를 확인하여 파일 유출 여부를 검증했다.

다음 명령어를 이용하여 이미지의 상세 정보를 확인할 수 있다.

```bash
identify -verbose image.png
```

결과에서 이미지 프로필과 관련된 정보를 확인하고, 해당 데이터가 인코딩되어 있는 경우 이를 적절한 형식으로 변환하여 내용을 분석할 수 있다.

이 과정을 통해 단순한 이미지 업로드 기능에서도 **서버 측 파일 처리 로직의 취약점이 정보 유출로 이어질 수 있음**을 확인할 수 있다.

# 10. 버그헌팅 윤리 및 주의사항

## 10.1. 시스템 보호

버그헌팅과 침투 테스트의 목적은 시스템을 파괴하는 것이 아니라 취약점을 발견하고 보안성을 향상시키는 것이다.

따라서 취약점 검증 과정에서 다음과 같은 실제 피해를 발생시키는 행위를 피해야 한다.

- 서비스 거부(DoS)
- 데이터 삭제
- 개인정보 수집
- 과도한 시스템 자원 사용
- 다른 사용자의 계정이나 데이터 접근
- 운영 환경에 대한 불필요한 변경

## 10.2. 개인정보 보호

취약점 검증 과정에서 다른 사용자의 개인정보나 민감한 데이터를 발견하더라도 불필요하게 열람하거나 수집해서는 안 된다.

취약점의 존재를 증명하는 데 필요한 최소한의 정보만 확인하고, 추가적인 데이터 접근은 중단해야 한다.

## 10.3. Bug Bounty 정책 준수

버그헌팅에서는 해당 기업이나 서비스가 제시한 **Bug Bounty Policy와 테스트 범위**를 반드시 확인해야 한다.

예를 들어 다음과 같은 조건이 존재할 수 있다.

- 특정 파일명 사용
- 특정 User-Agent 사용
- 테스트 가능한 도메인 제한
- 특정 API만 테스트 허용
- 자동화 도구 사용 제한
- 개인정보 접근 금지

## 10.4. 책임 있는 보안 연구

좋은 의도를 가지고 있더라도 정해진 범위를 벗어나 실제 피해를 발생시키면 문제가 될 수 있다.

따라서 항상 다음 원칙을 지켜야 한다.

> **허가된 범위에서 최소한의 영향으로 취약점을 검증한다.**

# 11. 핵심내용 (Summary)

1. **기본 설정의 위험성:** 오픈소스 소프트웨어나 프레임워크에서 기본 Secret Key나 암호화 관련 비밀값을 변경하지 않고 사용하는 것은 인증 및 데이터 보호 체계를 약화시킬 수 있다.

2. **취약점은 체이닝을 통해 영향이 확대될 수 있다:** 인증 우회 → 관리자 권한 → 데이터베이스 기능 → 시스템 영역과 같이 여러 기능이 연결되면서 하나의 취약점이 더 큰 영향으로 이어질 수 있다.

3. **XSS의 영향 범위를 함께 분석해야 한다:** XSS는 단순히 스크립트를 실행하는 것에서 끝나는 것이 아니라 피해자의 권한으로 수행되는 요청이나 관리자 기능과 결합하여 더 큰 영향을 발생시킬 수 있다.

4. **SSTI는 서버 측 코드 실행으로 이어질 수 있다:** VMware Workspace ONE Access 사례는 템플릿 엔진을 사용할 때 사용자 입력을 안전하게 처리하고 템플릿 엔진의 기능과 권한을 적절하게 제한해야 함을 보여준다.

5. **논리적 취약점도 큰 영향을 줄 수 있다:** ImageMagick 사례처럼 메모리 커럽션과 같은 복잡한 취약점이 아니더라도, 특정 메타데이터 처리 로직의 문제만으로 서버 내부 파일이 노출될 수 있다.

6. **공개된 Exploit은 환경에 맞게 분석해야 한다:** Metasploit 모듈이나 PoC가 모든 환경에서 그대로 동작하는 것은 아니다. `reload_all`을 통한 외부 모듈 로드, Burp Suite를 이용한 패킷 분석, 인코딩 확인 등을 통해 실패 원인을 직접 분석하는 능력이 중요하다.

7. **메타데이터도 보안 대상이다:** 이미지와 같은 파일을 서버에서 처리할 때 생성되는 메타데이터에는 민감한 정보가 포함될 수 있으므로, 파일 처리 과정과 결과물에 불필요한 정보가 남지 않도록 관리해야 한다.

8. **도구보다 원리 이해가 중요하다:** PoC나 Metasploit을 단순히 실행하는 것보다 취약점의 원인, 데이터 흐름, 서버의 처리 과정, 실패 원인을 이해하는 것이 중요하다.

9. **윤리적 해킹의 기본은 범위 준수이다:** 버그헌팅은 실제 시스템에 피해를 주는 활동이 아니라 취약점을 안전하게 검증하고 제보하는 활동이다. 테스트 범위와 기업의 정책을 준수하고 최소한의 영향으로 검증해야 한다.
