## 2. 웹 애플리케이션의 기본 구조 및 작동 원리

### 웹(Web)의 정의

웹(Web)은 HTTP 프로토콜을 이용하여 정보를 공유하는 서비스이다.

정보를 제공하는 측을 웹 서버(Web Server), 정보를 요청하고 전달받는 측을 웹 클라이언트(Web Client)라고 한다.

### 웹의 진화와 보안의 중요성

- 초기의 웹은 단순한 문서 공유 형태로 시작했지만, 현재는 금융, 쇼핑, SNS 등 복잡한 서비스로 발전했다.
- 웹을 통해 집 주소, 카드 번호, 계정 정보 등 민감한 개인정보(PII)가 전송되기 때문에 정보 유출을 방지하기 위한 웹 보안의 중요성이 높아졌다.

### 프론트엔드(Front-end)와 웹 리소스

프론트엔드는 사용자가 직접 보고 상호작용하는 부분으로, HTML, CSS, JavaScript 등의 웹 리소스로 구성된다.

- `404 Not Found`: 요청한 리소스를 서버에서 찾을 수 없다는 의미이다.
- URL을 통해 특정 리소스에 접근하면 클라이언트가 서버에 해당 리소스를 요청하게 된다.

---

## 3. 웹 리소스의 3대 요소 (HTML, CSS, JS)

프론트엔드를 구성하는 핵심 기술은 HTML, CSS, JavaScript이다.

### 1. HTML (HyperText Markup Language)

웹 문서의 구조와 뼈대를 담당한다.

태그와 속성을 이용하여 웹 페이지의 구조화된 문서를 작성한다.

### 2. CSS (Cascading Style Sheets)

웹 문서의 시각적인 표현을 담당한다.

글자 크기, 색상, 배경, 배치 등의 스타일을 지정한다.

### 3. JavaScript (JS)

웹 문서의 동작을 정의한다.

사용자의 클릭, 스크롤 등의 이벤트를 처리하고 서버와 데이터를 주고받는 등의 기능을 구현한다.

> **전문가 Tip:** 클라이언트 사이드 취약점인 XSS 등을 분석하기 위해서는 JavaScript와 HTML에 대한 이해가 중요하다.

## 4. URI (Uniform Resource Identifier)의 구조

### URI의 정의

URI(Uniform Resource Identifier)는 인터넷 자원을 식별하기 위한 문자열이다.

URL(Uniform Resource Locator)은 URI의 하위 개념으로, 자원의 위치를 나타내는 URI이다.

### URI의 상세 구조

URI는 일반적으로 다음과 같은 구조로 표현한다.

```text
scheme://user:password@host:port/path?query#fragment
```

### 1. Scheme (스킴)

사용할 프로토콜 또는 URI의 처리 방식을 나타낸다.

예를 들어 다음과 같은 스킴이 있다.

- `http`
- `https`
- `ftp`

### 2. User (유저 정보)

사용자 이름과 비밀번호 등을 나타내는 영역이다.

현재 웹 환경에서는 보안상의 이유 등으로 대부분 사용하지 않는다.

### 3. Host (호스트)

접속할 대상의 도메인 이름 또는 IP 주소를 나타낸다.

예:

```text
example.com
192.168.0.10
```

### 4. Port (포트)

서비스가 사용하는 포트 번호를 나타낸다.

포트를 생략하면 일반적으로 프로토콜의 기본 포트가 사용된다.

- HTTP: `80`
- HTTPS: `443`

### 5. Path (패스)

서버에서 요청할 리소스의 경로를 나타낸다.

예:

```text
/user/profile
/images/logo.png
```

### 6. Query (쿼리)

서버에 전달할 추가적인 정보를 나타낸다.

일반적으로 `?key=value` 형식으로 작성한다.

예:

```text
/search?keyword=test
```

### 7. Fragment (프래그먼트)

문서 내부의 특정 위치를 식별한다.

`#` 뒤에 작성하며 일반적으로 서버로 전송되지 않고 클라이언트 측에서 처리된다.

예:

```text
/page#section1
```

### URI 구조의 중요성

개발자가 URI의 각 구성 요소를 잘못 처리하면 다양한 웹 취약점이 발생할 수 있다.

따라서 웹 보안 연구에서는 URI의 각 요소가 서버에서 어떻게 처리되는지 이해하는 것이 중요하다.

## 5. HTTP 프로토콜과 메시지 구조

### HTTP의 정의

HTTP(HyperText Transfer Protocol)는 클라이언트와 서버가 요청(Request)과 응답(Response)을 주고받기 위한 통신 규칙이다.

### HTTP 메시지 구조

HTTP 메시지는 크게 Header와 Body로 구성된다.

### CRLF

HTTP 헤더의 각 줄은 `\r\n`(Carriage Return + Line Feed)으로 구분한다.

헤더가 끝난 후 빈 줄을 표시하여 헤더와 본문을 구분한다.

### Header

헤더는 필드와 값으로 구성되며 요청이나 응답에 대한 다양한 정보를 전달한다.

예:

```text
Content-Type: application/json
User-Agent: Mozilla/5.0
```

### Body

헤더가 끝난 뒤에 위치하며 실제로 전달할 데이터가 들어간다.

HTML, JSON, 파일 데이터 등이 Body에 포함될 수 있다.

### HTTPS와 TLS

HTTP는 기본적으로 암호화되지 않은 통신을 수행하기 때문에 네트워크에서 데이터가 노출될 위험이 있다.

HTTPS는 HTTP를 TLS(Transport Layer Security) 위에서 동작하도록 하여 통신 내용을 보호한다.

## 6. DNS (Domain Name System)의 원리

### DNS의 정의

DNS(Domain Name System)는 사람이 읽기 쉬운 도메인 이름을 IP 주소로 확인할 수 있도록 하는 시스템이다.

예:

```text
google.com → IP 주소
```

### DNS 작동 과정

예를 들어 사용자가 `www.google.com`에 접속하는 경우 다음과 같은 과정이 진행될 수 있다.

1. 브라우저 또는 운영체제가 DNS 캐시를 확인한다.
2. 필요한 경우 설정된 DNS 서버(Local DNS)에 질의한다.
3. DNS 서버에 정보가 없으면 Root DNS 서버를 통해 `.com` TLD 서버의 정보를 확인한다.
4. `.com` 서버를 통해 `google.com`을 관리하는 권한 있는 DNS 서버를 확인한다.
5. 최종적으로 `www.google.com`의 IP 주소를 확인한다.
6. 확인한 IP 주소를 이용하여 서버에 접속한다.

### 주요 DNS 레코드

#### A Record

도메인 이름을 IPv4 주소와 연결한다.

```text
example.com → 192.168.0.10
```

#### CNAME (Canonical Name)

하나의 도메인 이름을 다른 도메인 이름의 별칭으로 연결한다.

```text
www.example.com → example.com
```

CNAME은 클라우드 서비스나 CDN 등 다른 도메인을 대상으로 서비스를 연결할 때 활용할 수 있다.

> **전문가 Tip:** DNS 설정이 잘못되거나 더 이상 사용하지 않는 외부 서비스와 연결된 서브도메인이 방치되면 서브도메인 테이크오버와 같은 보안 문제가 발생할 수 있다.

## 7. 웹 아키텍처: 클라이언트와 서버의 역할 분담

웹 서비스는 일반적으로 클라이언트의 요청을 서버가 처리하고 결과를 반환하는 구조로 동작한다.

### 웹 서버 (Web Server)

웹 서버는 클라이언트의 요청을 가장 앞단에서 처리한다.

예:

- Nginx
- Apache HTTP Server

주요 역할은 다음과 같다.

- HTML, CSS, JavaScript, 이미지 등의 정적 콘텐츠 제공
- 클라이언트 요청 처리
- 동적 요청을 WAS로 전달

### 웹 애플리케이션 서버 (WAS)

WAS(Web Application Server)는 웹 애플리케이션의 비즈니스 로직을 처리한다.

예:

- Apache Tomcat
- Django
- Node.js

사용자의 요청에 따라 데이터베이스에서 데이터를 조회하거나 데이터를 처리한 후 결과를 생성한다.

### 데이터베이스 (DB)

데이터베이스는 서비스에서 사용하는 데이터를 저장하고 관리한다.

WAS가 필요한 데이터를 DB에 요청하고 결과를 받아 사용자에게 전달한다.

### 기본적인 구조

```text
Client
   ↓
Web Server
   ↓
WAS
   ↓
Database
```

각 계층에서 인증, 인가, 입력값 검증, 설정 오류 등의 다양한 취약점이 발생할 수 있다.

## 8. HTTP GET 요청: 정보 조회

### 특징

GET은 서버에서 리소스를 조회할 때 사용하는 HTTP Method이다.

### 데이터 전송

일반적으로 URL의 Query Parameter를 이용하여 데이터를 전달한다.

예:

```text
/search?keyword=test
```

### 주요 특성

#### 캐싱

GET 요청은 캐시될 수 있다.

동일한 요청의 결과를 캐시하면 서버에 다시 요청하지 않고 저장된 결과를 사용할 수 있다.

#### 기록 및 공유

URL에 요청 정보가 포함될 수 있기 때문에 브라우저의 방문 기록이나 북마크 등에 남을 수 있다.

#### 멱등성 (Idempotency)

GET은 HTTP 의미론상 멱등적인 메서드이다.

동일한 요청을 여러 번 수행하더라도 서버의 상태가 계속해서 변경되도록 설계하지 않는 것이 일반적이다.

#### 보안상 주의사항

URL에 포함된 Query Parameter는 브라우저 기록, 로그, 프록시 등의 여러 위치에 남을 수 있다.

따라서 비밀번호, 세션 토큰 등의 민감한 정보를 GET URL에 포함해서는 안 된다.

## 9. HTTP 응답(Response) 구조

서버는 클라이언트의 요청을 처리한 후 HTTP Response를 반환한다.

### 1. 상태 코드 (Status Code)

요청을 처리한 결과를 3자리 숫자로 나타낸다.

예:

- `200`: 정상 처리
- `404`: 리소스를 찾을 수 없음
- `500`: 서버 내부 오류

### 2. Header

응답에 대한 메타데이터를 전달한다.

예:

- Content-Type
- Cache-Control
- Set-Cookie

### 3. Body

실제 응답 데이터가 들어간다.

예:

- HTML
- JSON
- 이미지
- 파일

## 10. HTTP POST 요청: 데이터 전송 및 상태 변경

### 특징

POST는 서버에 데이터를 전달하여 리소스를 생성하거나 서버의 상태를 변경할 때 주로 사용한다.

### 데이터 전송

일반적으로 요청 Body에 데이터를 포함한다.

예:

```http
POST /login HTTP/1.1
Content-Type: application/x-www-form-urlencoded

username=test&password=password
```

### 주요 특성

#### 데이터 크기

GET처럼 URL 길이에 직접적인 제약을 받는 방식은 아니므로 상대적으로 많은 데이터를 Body에 전달할 수 있다.

다만 실제 데이터 크기는 웹 서버, 애플리케이션, 프록시 등의 설정에 따라 제한될 수 있다.

#### 캐싱

POST 요청은 일반적으로 GET보다 캐싱되지 않지만, HTTP 표준상 모든 POST가 절대로 캐시될 수 없는 것은 아니다.

#### 브라우저 기록

POST 요청의 Body 데이터 자체가 일반적인 브라우저 방문 기록의 URL에 그대로 표시되는 것은 아니다.

그러나 요청 데이터가 서버 로그 등에 기록될 가능성이 있으므로 POST라고 해서 민감한 데이터가 자동으로 보호되는 것은 아니다.

#### 비멱등성

POST는 일반적으로 비멱등적인 메서드이다.

동일한 요청을 여러 번 보내면 여러 개의 리소스가 생성되는 등 서버 상태가 여러 번 변경될 수 있다.

> **참고:** 브라우저에서 POST 요청 이후 새로고침할 때 `"양식 다시 제출"`과 같은 경고가 나타나는 것은 이전 POST 요청을 다시 전송할 가능성이 있기 때문이다.

## 11. 기타 HTTP Method와 버그헌팅 전략

버그헌팅에서는 프로그램에서 사용하는 HTTP Method와 서버의 처리가 일치하는지 확인하는 것이 중요하다.

### PUT

리소스를 생성하거나 기존 리소스를 전체적으로 대체할 때 사용하는 메서드이다.

권한 검증이 제대로 이루어지는지 확인하는 과정에서 중요한 대상이 될 수 있다.

### DELETE

리소스를 삭제할 때 사용하는 메서드이다.

삭제 권한이 없는 사용자의 요청을 서버가 제대로 차단하는지 확인할 수 있다.

### OPTIONS

서버 또는 특정 리소스가 지원하는 HTTP Method 등의 정보를 확인하는 데 사용한다.

서버 설정에 따라 `PUT`, `DELETE` 등이 허용되어 있는지 확인하는 데 참고할 수 있다.

### TRACE

요청이 서버에서 어떻게 처리되는지 확인하기 위한 진단 목적의 메서드이다.

보안상 불필요한 경우 비활성화하는 것이 권장되며, 환경에 따라 요청 헤더가 반사되는 등의 문제가 발생할 수 있다.

## 12. 핵심 HTTP 헤더의 이해

### Set-Cookie

서버는 로그인 등의 과정에서 `Set-Cookie` 헤더를 사용하여 클라이언트에게 쿠키를 설정할 수 있다.

예:

```http
Set-Cookie: sessionid=abc123
```

### HttpOnly

`HttpOnly` 속성이 설정된 쿠키는 JavaScript의 `document.cookie`를 통해 직접 읽을 수 없다.

따라서 XSS가 발생하더라도 JavaScript를 통한 세션 쿠키 직접 탈취의 위험을 줄이는 데 도움이 된다.

다만 `HttpOnly`가 XSS 자체를 방지하는 것은 아니다.

### User-Agent

User-Agent는 클라이언트가 사용하는 브라우저, 운영체제 등의 정보를 서버에 전달하는 HTTP 헤더이다.

서버가 User-Agent를 신뢰하여 접근 제어나 기능을 결정하도록 잘못 구현되어 있다면 보안 문제가 발생할 수 있다.

따라서 보안 연구에서는 User-Agent와 같은 클라이언트가 직접 전달할 수 있는 값을 서버가 어떻게 처리하는지 확인하는 것이 중요하다.

## 13. HTTP 응답 코드(Status Code) 분석

HTTP Status Code는 서버가 클라이언트의 요청을 어떻게 처리했는지를 나타내는 3자리 숫자이다.

### 200번대 - 성공

#### 200 OK

요청이 정상적으로 처리되었음을 의미한다.

### 300번대 - 리다이렉션

클라이언트가 요청을 완료하기 위해 추가적인 동작이 필요함을 나타낸다.

#### 302 Found

요청한 리소스가 다른 위치에 있으므로 클라이언트가 해당 위치로 다시 요청하도록 지시한다.

### 400번대 - 클라이언트 오류

클라이언트의 요청에 문제가 있음을 나타낸다.

#### 400 Bad Request

요청 형식이 잘못되었음을 의미한다.

#### 401 Unauthorized

인증이 필요하거나 인증 정보가 유효하지 않음을 의미한다.

#### 403 Forbidden

서버가 요청을 이해했지만 해당 리소스에 대한 접근을 허용하지 않음을 의미한다.

#### 404 Not Found

요청한 리소스를 찾을 수 없음을 의미한다.

### 500번대 - 서버 오류

서버에서 요청을 처리하는 과정에서 문제가 발생했음을 나타낸다.

#### 500 Internal Server Error

서버 내부에서 예외 또는 오류가 발생했음을 의미한다.

#### 503 Service Unavailable

서버가 일시적으로 요청을 처리할 수 없는 상태임을 의미한다.

---

## 14. 버그헌팅 관점에서의 응답 코드 해석

HTTP 상태 코드는 단순히 성공과 실패를 확인하는 용도뿐만 아니라 서버의 동작을 분석하는 단서로 활용할 수 있다.

### 이상 징후 확인

인증이 필요한 페이지에 접근했을 때 예상과 다른 상태 코드가 반환된다면 인증 및 인가 로직을 확인할 필요가 있다.

예를 들어 인증되지 않은 사용자가 특정 리소스에 접근했을 때 `200 OK`가 반환된다면 접근 통제가 제대로 이루어지고 있는지 확인해야 한다.

### 404 응답 분석

존재하지 않는 경로에 접근했을 때 `404 Not Found`가 반환된다.

응답의 차이, 응답 본문, 응답 크기, 헤더 등을 비교하면 서버가 경로를 어떻게 처리하는지 파악하는 데 도움이 될 수 있다.

예를 들어 다음과 같은 URL 구조를 발견했다면:

```text
/user/1
/user/2
/user/3
```

동일한 구조를 가진 다른 리소스가 존재하는지 확인하는 방식으로 애플리케이션의 구조를 분석할 수 있다.

### 에러 페이지 정보 노출

기본 404 또는 500 페이지가 아닌 개발자가 작성한 에러 페이지에서 다음과 같은 정보가 노출되는지 확인할 수 있다.

- 서버 버전
- 프레임워크 정보
- 내부 경로
- 내부 IP
- Stack Trace
- 디버깅 정보

이러한 정보가 불필요하게 외부에 노출되면 정보 노출 취약점으로 이어질 수 있다.

## 15. 프록시(Proxy)의 개념과 역할

### 일반적인 통신

일반적인 웹 통신은 클라이언트와 서버가 직접 통신하는 형태로 표현할 수 있다.

```text
Client ↔ Server
```

### 프록시 통신

프록시를 사용하는 경우 클라이언트와 서버 사이에 프록시가 위치한다.

```text
Client ↔ Proxy ↔ Server
```

프록시는 클라이언트와 서버 사이에서 HTTP 요청과 응답을 중계할 수 있다.

### 보안 분석에서의 활용

웹 보안 분석에서는 프록시를 이용하여 서버로 전달되기 전에 요청을 확인하고 수정할 수 있다.

또한 서버에서 반환된 응답을 확인하여 애플리케이션의 동작을 분석할 수 있다.

## 16. Burp Suite 실습 및 핵심 기능

Burp Suite는 웹 애플리케이션의 보안 테스트에 널리 사용되는 프록시 기반 분석 도구이다.

### 설정 및 구동

Burp Suite를 실행한 후 다음과 같이 사용할 수 있다.

```text
Next → Start Burp
```

Burp Suite의 `Proxy → Open Browser` 기능을 사용하면 별도의 브라우저 프록시 설정 없이 내장 브라우저를 이용하여 HTTP 요청을 확인할 수 있다.

### Intercept

`Intercept is on` 상태에서는 클라이언트의 요청이 서버로 전달되기 전에 Burp Suite에서 일시적으로 멈춘다.

예를 들어 검색어를 입력하면 해당 HTTP Request를 확인하고 필요한 경우 수정할 수 있다.

Response를 확인하려면 환경에 따라 서버 응답 인터셉트 관련 설정을 활성화해야 한다.

### Repeater

Repeater는 하나의 HTTP 요청을 반복적으로 전송하면서 요청 값을 수정하고 서버의 응답을 비교하는 기능이다.

사용 방법:

```text
요청 우클릭 → Send to Repeater
```

예를 들어 검색어가 다음과 같이 전달된다면:

```text
test
```

Repeater에서 값을 다음과 같이 변경하여 서버의 반응을 비교할 수 있다.

```text
asdasd
```

브라우저에서 매번 같은 동작을 반복하지 않고 요청을 직접 수정할 수 있다는 점이 장점이다.

### Intruder

Intruder는 여러 입력값을 자동으로 대입하여 서버의 반응을 비교하는 자동화 기능이다.

사용 방법:

```text
요청 우클릭 → Send to Intruder
```

#### 설정 방법

1. 변조할 파라미터 값을 지정하여 Payload Position을 설정한다.
2. Payloads 탭에서 대입할 값을 입력한다.
3. Start Attack을 실행한다.
4. 각각의 요청에 대한 서버 응답을 비교한다.

예:

```text
123
234
test
```

Intruder는 허가된 환경에서 퍼징(Fuzzing)이나 입력값 검증 테스트 등을 수행할 때 활용할 수 있다.

## 17. 인증 (Authentication): 신원 확인

### 인증의 정의

인증(Authentication)은 사용자가 본인이 주장하는 사람인지 확인하는 과정이다.

예:

- ID / Password
- OTP
- 지문
- 보안 토큰

### 세션 관리의 필요성

HTTP는 기본적으로 Stateless한 프로토콜이므로 서버가 각각의 요청을 자동으로 동일한 사용자로 인식하지 않는다.

따라서 웹 애플리케이션은 쿠키와 세션 등의 기술을 이용하여 사용자의 상태를 관리한다.

### 1. 쿠키 (Cookie)

쿠키는 웹 브라우저에 저장되는 작은 데이터이다.

서버는 `Set-Cookie` 응답 헤더를 통해 쿠키를 설정할 수 있으며, 이후 클라이언트는 조건에 따라 해당 쿠키를 서버에 전송한다.

클라이언트 측에 저장되는 데이터이므로 서버는 쿠키 값을 신뢰해서는 안 된다.

### 2. 세션 (Session)

세션은 일반적으로 서버 측에 사용자 상태를 저장하고 클라이언트에는 세션을 식별하기 위한 세션 ID를 전달하는 방식이다.

세션 ID가 탈취되면 공격자가 해당 세션의 사용자로 가장할 수 있으므로 세션 ID는 중요한 인증 정보로 취급해야 한다.

### 주요 인증 취약점

#### 1. 세션 하이재킹 (Session Hijacking)

공격자가 사용자의 세션 ID를 탈취하여 해당 사용자로 위장하는 공격이다.

세션 ID는 XSS, 악성 확장 프로그램, 잘못된 로그 관리 등 다양한 경로를 통해 노출될 수 있다.

#### 2. 무차별 대입 (Brute Force)

가능한 비밀번호 조합을 반복적으로 대입하여 인증을 우회하려는 공격이다.

비밀번호 정책이 약하거나 로그인 시도 제한 및 추가적인 보호 장치가 부족하면 위험이 증가한다.

#### 3. MFA 우회

MFA(Multi-Factor Authentication)를 사용하더라도 인증 과정의 로직에 문제가 있으면 우회 가능성이 발생할 수 있다.

예를 들어 인증 상태를 제대로 검증하지 않거나 복구 및 재등록 절차를 부적절하게 설계하면 MFA의 보안 효과가 약화될 수 있다.

---

## 18. 인가 (Authorization): 권한 부여

### 인가의 정의

인가(Authorization)는 인증된 사용자가 특정 리소스나 기능을 사용할 수 있는지 결정하는 과정이다.

예:

- 파일 읽기
- 파일 수정
- 게시글 삭제
- 관리자 기능 접근

### 인증과 인가의 차이

```text
Authentication → 누구인가?
Authorization  → 무엇을 할 수 있는가?
```

### RBAC (Role-Based Access Control)

RBAC는 사용자의 역할(Role)을 기준으로 권한을 관리하는 방식이다.

예:

```text
관리자 → 사용자 관리 가능
일반 사용자 → 자신의 정보만 관리 가능
```

---

## 19. 최신 인가 및 인증 관련 기술

### 1. JWT (JSON Web Token)

JWT는 클레임 정보를 JSON 형태로 담고 이를 서명하여 전달하는 토큰 형식이다.

일반적으로 다음 세 부분으로 구성한다.

```text
Header.Payload.Signature
```

- Header: 토큰 타입과 서명 알고리즘 등의 정보를 포함한다.
- Payload: 사용자 또는 권한 등에 대한 Claim을 포함한다.
- Signature: 토큰의 무결성을 검증하기 위한 서명이다.

JWT 자체가 암호화를 의미하는 것은 아니며, 일반적인 JWT의 Payload는 Base64URL 인코딩되어 있으므로 민감한 정보를 그대로 넣어서는 안 된다.

### 2. OAuth 2.0

OAuth 2.0은 사용자의 비밀번호를 제3자 애플리케이션에 직접 제공하지 않고 특정 리소스에 대한 접근 권한을 위임하기 위한 권한 부여 프레임워크이다.

예를 들어 사용자가 특정 애플리케이션에 Google 계정의 일부 권한을 부여하는 상황에서 사용할 수 있다.

### 주요 구성 요소

- Resource Owner: 리소스 소유자
- Client: 권한을 요청하는 애플리케이션
- Resource Server: 보호된 리소스를 제공하는 서버
- Authorization Server: 권한 부여 및 토큰 발급을 담당하는 서버

### 일반적인 Authorization Code 흐름

```text
권한 요청
   ↓
사용자 인증 및 동의
   ↓
Authorization Code 발급
   ↓
Access Token 교환
   ↓
Resource Server API 이용
```

## 20. 입력값 검증 (Input Validation)

### 입력값 검증의 필요성

사용자가 입력하는 값은 기본적으로 신뢰해서는 안 된다.

검증되지 않은 입력값이 서버 내부 로직에 그대로 사용되면 다음과 같은 보안 문제가 발생할 수 있다.

- SQL Injection
- XSS
- Command Injection
- Path Traversal
- 서버 오류
- 권한 우회

### 취약점 예시: Directory Traversal

Directory Traversal은 파일 경로를 처리하는 과정에서 공격자가 상위 디렉터리를 나타내는 경로를 조작하여 의도하지 않은 파일에 접근하는 취약점이다.

대표적으로 다음과 같은 형태가 사용될 수 있다.

```text
../
```

운영체제와 애플리케이션의 처리 방식에 따라 민감한 파일에 접근할 가능성이 발생할 수 있다.

### 입력값 검증 전략

#### 1. 블랙리스트 (Blacklist)

위험하다고 판단되는 특정 문자열이나 패턴만 차단하는 방식이다.

예:

```text
SELECT
<script>
../
```

하지만 공격자는 다양한 인코딩이나 다른 표현을 이용하여 필터를 우회할 수 있으므로 단독 방어 수단으로 사용하기에는 한계가 있다.

#### 2. 화이트리스트 (Whitelist)

허용할 입력의 형태를 먼저 정의하고 그 외의 입력을 제한하는 방식이다.

예를 들어 숫자 ID만 허용하는 기능이라면 다음과 같이 입력 형식을 제한할 수 있다.

```text
0~9로 구성된 값만 허용
```

블랙리스트보다 예측 가능한 입력 범위를 설정할 수 있다는 장점이 있다.

### 입력값 검증 방법

다음과 같은 방법을 함께 활용할 수 있다.

- 정규 표현식(Regular Expression)
- 데이터 타입 제한
- 문자열 길이 제한
- 허용 문자 제한
- 서버 측 검증
- 적절한 인코딩 및 출력 처리

클라이언트 측 검증만으로는 보안을 보장할 수 없으며, 중요한 검증은 반드시 서버 측에서도 수행해야 한다.

# 핵심내용 (Summary)

## 1. 웹의 기본 구조

웹은 클라이언트와 서버가 HTTP를 이용하여 요청과 응답을 주고받는 구조로 동작한다.

웹 애플리케이션은 일반적으로 다음과 같은 계층으로 구성할 수 있다.

```text
Client
  ↓
Web Server
  ↓
WAS
  ↓
Database
```

각 계층에서 서로 다른 보안 취약점이 발생할 수 있으므로 전체 구조를 이해하는 것이 중요하다.

## 2. URI를 이해한다.

URI는 다음과 같은 구성 요소를 가진다.

```text
Scheme://User@Host:Port/Path?Query#Fragment
```

각 요소가 서버에서 어떻게 처리되는지 이해하면 웹 애플리케이션의 요청 구조와 취약점을 분석하는 데 도움이 된다.

## 3. HTTP Method의 특성을 이해한다.

- **GET:** 주로 리소스 조회에 사용한다.
- **POST:** 데이터 전달 및 상태 변경에 주로 사용한다.
- **PUT:** 리소스 생성 또는 전체 대체에 사용한다.
- **DELETE:** 리소스 삭제에 사용한다.
- **OPTIONS:** 지원되는 메서드 등의 정보를 확인하는 데 사용한다.
- **TRACE:** 요청 경로를 진단하기 위한 메서드이다.

## 4. HTTP 상태 코드를 분석한다.

- `200` → 정상 처리
- `302` → 리다이렉션
- `400` → 잘못된 요청
- `401` → 인증 필요
- `403` → 접근 거부
- `404` → 리소스 없음
- `500` → 서버 내부 오류
- `503` → 서비스 이용 불가

상태 코드뿐만 아니라 응답 본문, 헤더, 응답 크기 등의 차이를 함께 비교하면 서버의 동작을 분석하는 데 도움이 된다.

## 5. 프록시와 Burp Suite를 활용한다.

프록시는 클라이언트와 서버 사이에서 HTTP 요청과 응답을 확인할 수 있도록 한다.

Burp Suite에서는 다음 기능을 주로 활용한다.

- **Proxy:** 요청과 응답을 가로채고 분석한다.
- **Repeater:** 요청을 직접 수정하여 반복적으로 전송한다.
- **Intruder:** 여러 입력값을 자동으로 대입하여 테스트한다.

## 6. 인증과 인가를 구분한다.

```text
Authentication → 누구인가?
Authorization  → 무엇을 할 수 있는가?
```

인증이 정상적으로 이루어졌더라도 인가 검증이 제대로 이루어지지 않으면 다른 사용자의 데이터에 접근하거나 권한이 없는 기능을 사용할 수 있는 문제가 발생할 수 있다.

## 7. 모든 입력값을 신뢰하지 않는다.

사용자가 전달하는 다음과 같은 값은 모두 조작될 가능성이 있다.

- URL
- Query Parameter
- POST Body
- HTTP Header
- Cookie
- HTTP Method

따라서 서버 측에서 입력값을 적절하게 검증하고, 필요한 경우 화이트리스트 기반 검증과 데이터 타입 및 길이 제한 등을 적용해야 한다.

## 8. 버그헌팅에서는 기술보다 범위가 먼저이다.

웹 애플리케이션을 분석할 때는 먼저 **허가된 대상과 테스트 범위(Scope)**를 확인해야 한다.

취약점 테스트는 반드시 허가된 환경에서 수행하고, 발견한 취약점은 프로그램에서 지정한 절차에 따라 최소한의 영향으로 검증하고 신고해야 한다.
