4. 수업내용
4.1. IDOR (부적절한 직접 객체 참조)
● 정의: 사용자가 입력한 파라미터(ID 등)가 서버의 데이터베이스 키나 파일 등 내부 객체를 직접
참조할 때, 권한 검증 없이 이를 처리하여 발생하는 취약점입니다. 주로 접근 제어(Access
Control) 실패와 관련 있습니다.
● 공격 유형:
○ 수평적 권한 상승 (Horizontal): 나와 동일한 권한을 가진 다른 사용자의 데이터(예:
1001번 유저가 1003번 유저 정보 열람)를 탈취.
○ 수직적 권한 상승 (Vertical): 일반 사용자가 관리자 권한의 기능을 수행.
● 트리거 포인트: 숫자형 ID 변조가 가장 흔하지만, 사용자 이름, 파일명 변경, HTTP
메서드(GET/POST) 변경, 콘텐츠 타입(JSON/XML) 변경 등으로도 발생할 수 있습니다.
35
4.2. XSS (크로스 사이트 스크립팅)
● 정의: 공격자가 웹 페이지에 악성 스크립트(JS)를 삽입하여, 이를 열람하는 희생자의
브라우저에서 실행되게 만드는 공격입니다. 정보 탈취나 세션 하이재킹에 주로 쓰입니다.
● 주요 3가지 유형:
1. Reflected XSS (반사형): 악성 스크립트가 포함된 URL을 사용자가 클릭하면, 서버가
이를 반사하여 브라우저에서 실행됩니다. (일회성).
2. Stored XSS (저장형): 게시판 등에 악성 스크립트를 작성하여 서버 DB에 저장하고,
해당 글을 읽는 모든 사용자에게 피해를 줍니다. 파급력이 가장 큽니다.
3. DOM-based XSS: 서버를 거치지 않고, 브라우저 내의 DOM 객체(예:
location.hash)를 처리하는 과정에서 발생하는 클라이언트 측 취약점입니다. 서버
로그에 남지 않아 탐지가 어렵습니다.
4.3. CSRF (사이트 간 요청 위조)
● 정의: 사용자가 자신의 의지와 무관하게 공격자가 의도한 행위(비밀번호 변경, 계좌 이체 등)를
웹사이트에 요청하게 만드는 공격입니다.
● 메커니즘: 사용자가 이미 로그인된 상태(세션/쿠키 보유)라는 점을 악용합니다. 해커가 보낸
링크나 이미지를 클릭하는 순간, 사용자 브라우저의 쿠키를 이용해 몰래 요청이 전송됩니다.
4.4. SQL Injection (SQL 삽입)
● 정의: 입력값 검증 부재를 틈타 SQL 쿼리문의 일부를 조작하여, DB 정보를 탈취하거나 조작하는
공격입니다.
● 공격 기법 (6가지):
1. Boolean-based Blind: 참/거짓 결과에 따라 데이터를 추측.
2. Error-based: 일부러 에러를 유발하여 에러 메시지에 포함된 DB 정보를 획득.
3. Union-based: UNION 연산자를 이용해 다른 테이블의 정보를 합쳐서 조회.
4. Stacked Query: 세미콜론(;)으로 쿼리를 닫고 새로운 악성 쿼리를 추가 실행.
5. Time-based Blind: sleep() 등을 이용해 응답 시간 지연 여부로 참/거짓을 판별.
6. Inline Query: 쿼리 내부에 또 다른 쿼리를 삽입-.
● 팁: 입력값에 -1을 했을 때 계산된 결과가 나온다면, 해당 값이 정수형으로 연산되고 있음을
유추할 수 있습니다.
4.5. File Inclusion (파일 포함 공격)
● LFI (Local File Inclusion): 서버 내부의 로컬 파일(/etc/passwd 등)을 읽어오거나
실행합니다.
○ RCE 연계: 파일 업로드 기능으로 웹쉘을 올리거나, 서버 로그(Log Poisoning)에 PHP
코드를 심은 뒤 LFI로 불러와 실행시킬 수 있습니다.
● RFI (Remote File Inclusion): 외부 서버에 있는 악성 파일(웹쉘 등)을 원격으로 불러와
서버에서 실행시킵니다. 공격자가 자신의 서버에 shell.txt를 두고 타겟 서버가 이를 include
하게 만듭니다.
36
4.6. SSRF (서버 사이드 요청 위조)
● 정의: 공격자가 서버를 조종하여 서버가 내부 시스템(Internal Network)이나 외부 시스템에
요청을 보내게 만드는 취약점입니다.
● 위험성: 방화벽으로 보호받는 내부망 스캔, 클라우드 환경(AWS 등)의 메타데이터
서비스(169.254.169.254)에 접근하여 자격 증명(Credential)을 탈취하는 데 주로
악용됩니다.
5. 핵심내용 (Summary)
1. IDOR의 단순함과 위험성: 복잡한 해킹 기술 없이 파라미터 변조만으로 타인의 정보를 볼 수
있는, 가장 빈번하고 파괴적인 취약점입니다.
2. XSS와 CSRF의 차이: XSS는 '스크립트 실행'을 통해 정보를 탈취하고, CSRF는 '사용자의
권한'을 도용하여 원치 않는 행위를 시킵니다.
3. Injection 계열의 위협: SQL Injection은 DB를, Command Injection이나 File Inclusion은
서버 자체를 장악할 수 있는 치명적인 공격입니다.
4. SSRF와 클라우드: 최근 클라우드 도입이 늘면서, 서버를 경유해 내부 클라우드 자원에 접근하는
SSRF 공격의 중요도가 매우 높아졌습니다.


4.1. 시나리오 개발의 중요성: 버그헌팅은 스토리텔링이다
● 단순 제보의 한계: "스크립트가 실행됩니다" 정도의 보고서는 낮은 평가를 받거나 거절될 수
있습니다. 담당자를 설득하려면 발생 가능한 결과(Impact)를 보여줘야 합니다.
● 상황 예시 (XSS와 HttpOnly):
○ 상황: XSS 취약점을 찾았으나, 세션 쿠키에 HttpOnly 옵션이 설정되어 있어
document.cookie로 세션을 탈취할 수 없는 경우.
○ 하수: "XSS가 있습니다"라고 제보 $\rightarrow$ Low 또는 Medium 등급.
○ 고수 (시나리오 개발): 사이트를 더 뒤져서 개발용 페이지나 에러 페이지에서 세션 정보가
평문으로 노출되는 곳을 찾아냅니다. 그 후 XSS를 이용해 해당 페이지를
비동기(AJAX/XHR)로 호출하고, 응답값에서 세션을 파싱해 공격자 서버로 전송하는
코드를 짭니다.
○ 결과: 단순 스크립트 실행이 '세션 탈취 및 계정 장악' 시나리오로 격상되어
High~Critical 포상금을 받습니다.
4.2. 취약점 체이닝 (Vulnerability Chaining)의 개념
● 정의: 두 개 이상의 상대적으로 중요하지 않은 보안 이슈를 결합하여 강력한 공격 시나리오를
구축하는 기법입니다.
● 효과: 단일 취약점으로는 제한적인 권한만 얻을 수 있지만, 체이닝을 하면 그 효과가
기하급수적으로 증가합니다.
● 이론적 체이닝 예시 (File Write + LFI):
1. Arbitrary File Write: 서버에 파일을 쓸 수 있지만, 방화벽 때문에 실행하거나 접근할
수 없는 상태.
2. LFI (Local File Inclusion): 파일을 실행할 수 있지만, 업로드할 방법이 없는 상태.
3. Chain: 파일 쓰기 취약점으로 악성 PHP 코드를 서버에 심고, LFI 취약점을 이용해 그
파일을 불러와 실행(RCE)시킵니다.
4.3. Self-XSS의 이해와 한계
● 정의: 공격자가 아닌 피해자 본인의 브라우저 콘솔 등에 스크립트를 직접 입력해야만 실행되는
XSS입니다.
● 한계: 피해자가 스스로 공격 코드를 입력해야 하므로, 이는 기술적 취약점이라기보다 피싱(Social
Engineering)에 가깝습니다. 따라서 대부분의 버그바운티 프로그램에서 포상 제외 대상(Out of
Scope)입니다.
● 반전: 하지만 이 Self-XSS도 다른 취약점과 결합되면 강력한 무기가 됩니다.
4.4. 실전 체이닝 사례: 우버(Uber) 계정 탈취 (2016)
본질적으로 위험도가 낮은 두 취약점을 연결하여 치명적인 결과를 만든 유명한 사례입니다.
● 취약점 1: Self-XSS
1. 우버 모바일 사이트(m.uber.com) 프로필 수정 기능에 XSS가 있었으나, 본인이
로그인했을 때만 실행되어 위협이 되지 않았습니다.
● 취약점 2: 헤더 조작 (Logout/Login CSRF 유사)
39
1. 로그아웃 등의 기능에서 파라미터를 조작해 응답 헤더(Set-Cookie)를 변조할 수 있는
취약점 발견. 공격자가 피해자의 브라우저 쿠키를 강제로 공격자의 세션으로 덮어씌울 수
있었습니다.
● Chaining Scenario (계정 탈취):
1. 공격자는 자신의 계정 프로필에 XSS 공격 코드(피해자의 OAuth 토큰을 훔치는 코드)를
심어놓습니다.
2. 피해자에게 헤더 조작 취약점이 있는 URL을 보냅니다.
3. 피해자가 클릭하면 Set-Cookie 헤더에 의해 강제로 공격자의 계정으로 로그인됩니다.
4. 로그인되자마자 공격자가 심어둔 XSS 코드가 피해자 브라우저에서 실행됩니다.
5. 이 XSS 코드는 피해자의 원래 쿠키 저장소 등에 남아있던 민감한 OAuth 토큰 등을
탈취하여 공격자에게 전송합니다.
● 결과: 단순 버그 2개를 엮어 원클릭 계정 탈취를 증명했습니다.
5. 핵심내용 (Summary)
1. 임팩트(Impact) 중심: 버그헌팅의 핵심은 "문제가 있다"는 통보가 아니라, "이 문제로 어떤
피해를 입힐 수 있다"는 증명입니다. 시나리오가 포상금의 액수를 결정합니다.
2. 취약점 체이닝: 낮은 등급의 취약점(Self-XSS, Open Redirect, Info Leak 등)들을 버리지 말고
기록해 두었다가, 서로 연결하여 Critical한 공격 벡터를 만들어야 합니다.
3. 시스템 이해: 체이닝을 위해서는 시스템의 비즈니스 로직과 데이터 흐름을 완벽히 이해하고, "내가
공격자라면 어떻게 이 서비스를 무너뜨릴까?"라고 끊임없이 질문해야 합니다.
