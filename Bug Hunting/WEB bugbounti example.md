# 1. 버그헌팅 통계와 트렌드

## 1.1. 지속적인 위협 XSS

● **XSS의 지속적인 발생:** 보안 기술이 발전하고 프레임워크 단에서 방어 로직을 갖추었음에도 불구하고, XSS(교차 사이트 스크립팅)는 여전히 많이 제보되고 발견되는 취약점 중 하나이다.

이는 공격자들이 필터링과 방어 로직을 우회하는 새로운 기법을 지속적으로 찾아내기 때문이다.

## 1.2. 권한 관리의 허점

● **IDOR과 접근 제어 취약점:** IDOR(부적절한 직접 객체 참조)과 같은 인증 및 접근 통제 관련 취약점 또한 빈번하게 보고된다.

특히 단순한 파라미터 변조만으로 다른 사용자의 데이터에 접근할 수 있는 경우가 있어 지속적인 점검이 필요하다.

# 2. IDOR 사례: 유튜브 비공개 영상 탈취 (Google)

## 2.1. 배경

유튜브에는 `비공개(Private)` 영상 설정이 존재하며, 허가된 사용자 외에는 영상을 볼 수 없어야 한다.

## 2.2. 발견 지점

취약점은 유튜브 자체가 아닌 연동된 `Google Ads` 서비스에서 발견되었다.

유튜버가 광고 삽입 시점을 설정하는 `Mark Moment` 기능이 문제의 원인이 되었다.

## 2.3. 공격 원리

1. `Mark Moment` 버튼을 누르면 `GetThumbnails`라는 POST 요청이 전송된다.
2. 요청 Body에는 영상 고유 ID와 타임스탬프(밀리초)가 포함된다.
3. 서버는 해당 시점의 썸네일 이미지를 Base64로 인코딩하여 응답한다.
4. 공격자는 타겟 비공개 영상의 ID를 알아낸 뒤 타임스탬프를 일정한 간격으로 변경하며 반복 요청을 보냈다.
5. 이렇게 수집한 썸네일들을 이어 붙여 비공개 영상의 내용을 복원할 수 있었다.

## 2.4. 교훈

메인 서비스가 안전하게 설계되어 있더라도, 연동된 서드파티 서비스에서 발생하는 논리적 허점을 통해 보안 통제를 우회할 수 있다.

따라서 버그헌팅에서는 메인 서비스뿐만 아니라 연동된 서비스와 API의 동작까지 함께 분석하는 것이 중요하다.

# 3. XSS 사례: 그누보드

## 3.1. 취약점 개요

● **대상:** 그누보드(GnuBoard)

● **유형:** Reflected XSS

● **발생 시점:** 2023년 4월 패치 사례

## 3.2. 발생 원인

`bbs/search.php` 페이지에서 `wr_table` 파라미터에 대한 검증이 충분하지 않아 발생했다.

## 3.3. 코드 분석

○ 사용자가 입력한 `wr_table` 값이 별도의 적절한 검증 없이 변수에 저장된다.

○ 해당 변수가 `get_paging` 함수의 인자로 전달된다.

○ 이후 해당 값이 HTML `<a>` 태그 내부에 안전하게 처리되지 않은 상태로 삽입되어 출력되면서 XSS가 발생할 수 있다.

## 3.4. 패치

해당 파라미터에 정규식(`preg_replace`) 등을 적용하여 허용되지 않는 특수문자가 입력되지 않도록 제한하는 방식으로 문제를 해결했다.

# 4. SQL Injection 사례: Sony RCE 연계

## 4.1. 정찰(Recon)의 중요성

제보자는 처음에 `Sublist3r`를 사용했으나 유효한 도메인을 찾지 못했다.

이후 `Amass`를 사용하여 검색엔진에 노출되지 않은 숨겨진 서브도메인을 발견했다.

이를 통해 버그헌팅에서 정찰 단계(Recon)가 공격 표면을 찾는 중요한 과정임을 확인할 수 있다.

## 4.2. 취약점 탐지

1. 로그인 페이지의 `username` 파라미터에 작은따옴표(`'`)를 입력했을 때 500 에러와 함께 SQL 구문 오류가 노출되었다.
2. 오류 내용을 분석하여 데이터베이스가 MS-SQL임을 확인했다.
3. 하지만 `username` 파라미터 자체에는 필터링이 적용되어 있어 해당 파라미터만으로는 추가적인 공격이 어려운 상태였다.

## 4.3. 우회 및 에스컬레이션 (User-Agent)

1. 개발 과정에서 HTTP 헤더에 대한 입력 검증이 충분하지 않을 가능성을 고려했다.
2. `User-Agent` 헤더 값이 서버 측 SQL 쿼리에 사용되는지 확인했다.
3. 해당 입력 지점에서 SQL Injection 가능성을 확인했다.
4. Time-based SQL Injection을 통해 서버의 응답 시간 차이를 확인하여 취약점을 검증했다.
5. 이후 MSSQL의 기능을 악용하여 시스템 명령 실행으로 이어지는 RCE 가능성을 확인했다.

## 4.4. 결과

단순한 SQL Injection에 그치지 않고 서버 측 명령 실행으로 이어질 수 있음을 증명하여 취약점의 Impact를 크게 확장한 사례이다.

# 5. 핵심내용 (Summary)

1. **서드파티의 위험성:** 메인 서비스가 안전하더라도 연동된 서비스에서 발생하는 취약점을 통해 데이터가 유출될 수 있으므로 다양한 공격 벡터를 탐색해야 한다.

2. **HTTP 헤더의 중요성:** 입력 폼뿐만 아니라 `User-Agent`, `Cookie`, `Referer` 등과 같은 HTTP 헤더 값도 서버의 데이터베이스나 로직에서 처리될 수 있으므로 점검 대상에 포함해야 한다.

3. **도구의 적절한 활용:** 정찰 단계에서 `Amass`와 같은 도구를 활용하여 숨겨진 서브도메인이나 자산을 발견하는 것이 버그헌팅의 중요한 시작점이 될 수 있다.

4. **Impact 극대화:** 단순한 오류 발견에 그치지 않고, 해당 취약점이 실제로 어떤 보안 영향으로 이어질 수 있는지 증명하는 것이 중요하다.


# 6. [Sony] SQL Injection을 통한 RCE

## 6.1. 탐지 (Detection)

○ 로그인 페이지에서 `username` 파라미터에 작은따옴표(`'`)와 주석(`--`)을 입력했을 때 MSSQL 특유의 SQL 처리 방식과 에러 메시지를 통해 SQL Injection 가능성을 확인했다.

○ 이후 시간 지연을 이용한 테스트를 통해 Time-based SQL Injection을 확인했다.

## 6.2. 확장 (Escalation to RCE)

○ 단순한 데이터 유출에 그치지 않고 MSSQL 환경에서 시스템 명령 실행이 가능한 기능이 활성화되어 있는지 확인하여 RCE 가능성을 검증했다.

○ 외부 연결 및 현재 실행 계정 등의 정보를 확인하여 원격 코드 실행이 가능한 상태임을 증명했다.

## 6.3. 우회 (Bypass WAF)

○ 패치 이후 특정 명령어 문자열이 차단되자 문자열을 직접 입력하는 대신 다른 형태로 구성하여 필터링 로직을 우회할 수 있는 가능성을 확인한 사례이다.

이처럼 단순히 특정 문자열을 차단하는 방식의 방어는 다양한 입력 표현을 충분히 고려하지 않으면 우회될 수 있다.


# 7. [GitLab] Path Traversal을 통한 RCE

## 7.1. 취약점 배경

GitLab 엔터프라이즈 버전의 패키지 레지스트리 기능에서 Path Traversal 취약점이 발생한 사례이다.

## 7.2. 공격 원리

○ 공격자는 패키지를 업로드하는 과정에서 URL 경로에 상위 디렉터리를 나타내는 경로 조작 문자를 삽입했다.

○ 코드 분석 결과 GitLab에서 사용하는 프레임워크가 특정 파일명 파라미터에 대해서는 검증을 수행하지만, 실제 파일 경로에 대해서는 충분한 검증을 수행하지 않는 논리적 허점이 존재했다.

## 7.3. 임팩트 (Impact)

○ 공격자가 임의의 위치에 파일을 작성할 수 있는 경우, 서버의 중요 파일을 덮어쓰는 공격으로 이어질 수 있다.

○ 특히 SSH 인증 관련 파일과 결합될 경우 공격자가 서버에 인증된 접근을 확보할 가능성이 있으며, 결과적으로 시스템 장악으로 이어질 수 있다.

이 사례는 단순한 Path Traversal이 임의 파일 쓰기와 결합되었을 때 매우 높은 Impact를 가질 수 있음을 보여준다.


# 8. [Dropbox] SSRF 방어 우회

## 8.1. 탐지 (Detection)

○ Dropbox의 문서 불러오기 기능에서 외부 클라우드 서비스와 연동하는 과정에서 SSRF 가능성을 확인한 사례이다.

○ 단순히 외부 URL을 입력했을 때는 요청이 차단되었지만, 요청 파라미터를 변경하면서 방어 로직의 허점을 확인했다.

## 8.2. 목표 설정 (Targeting AWS)

○ 해당 서비스가 AWS 환경에서 동작한다는 점을 확인하고, AWS EC2 인스턴스의 메타데이터 서비스가 SSRF의 공격 대상이 될 수 있음을 고려했다.

○ 클라우드 환경의 메타데이터 서비스에는 인스턴스의 자격 증명과 관련된 민감한 정보가 존재할 수 있으므로 SSRF와 결합될 경우 위험도가 크게 증가할 수 있다.

## 8.3. 우회 (Redirect Bypass)

○ 직접적인 내부 IP 호출이 차단되는 경우에도 서버가 외부 서버의 HTTP Redirect를 따라가도록 구현되어 있다면 SSRF 방어가 우회될 가능성이 있다.

○ 공격자가 제어하는 서버가 HTTP `303 Redirect` 응답을 반환하여 다른 목적지로 요청을 전달하도록 만드는 방식으로 방어 로직을 우회할 수 있다.

○ 결과적으로 대상 서버가 외부에서 직접 접근하기 어려운 내부 자원으로 요청을 보내게 만들 수 있다.


# 9. 핵심내용 (Summary)

1. **임팩트의 극대화:** 세 사례 모두 단순한 취약점 발견에 그치지 않고, 시스템 장악(RCE)이나 클라우드 자격 증명 탈취 가능성과 같은 높은 수준의 Impact로 연결될 수 있음을 보여준다.

2. **창의적 우회:** 방화벽이나 필터링이 존재하더라도 단순한 문자열 차단이나 제한적인 검증에는 우회 가능성이 존재할 수 있으므로 방어 로직을 분석하는 것이 중요하다.

3. **깊이 있는 분석:** GitLab 사례처럼 소스 코드나 프레임워크의 동작 방식을 깊이 이해해야 발견할 수 있는 논리적 허점(Logic Flaw)이 존재한다.

4. **끈기(Persistence):** 예상한 결과가 나오지 않더라도 다른 파라미터나 입력 지점을 분석하고 방어 로직의 동작을 이해하는 과정이 버그헌팅에서 중요하다.
