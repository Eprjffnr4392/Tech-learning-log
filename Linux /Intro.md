# 1. Linux 시스템 보안 점검의 필요성

## 1.1. Linux의 높은 활용 범위

- Linux는 서버, 클라우드, IoT 등 다양한 환경에서 핵심 운영체제로 활용된다.
  - 웹 서버
  - 데이터베이스 서버
  - 컨테이너 인프라
  - 임베디드 장비
- 활용 범위가 넓을수록 공격자가 노릴 가치가 있는 시스템도 증가한다.
- 따라서 Linux 시스템의 보안 상태를 지속적으로 점검하고 관리하는 것이 중요하다.

## 1.2. 부적절한 설정과 관리

- 보안 사고는 새로운 기술의 취약점뿐만 아니라 **부적절한 설정과 관리**로 인해 발생하는 경우가 많다.
- 대표적인 문제는 다음과 같다.
  - 기본 설정을 그대로 사용하는 경우
  - 약한 비밀번호 정책을 사용하는 경우
  - 불필요한 서비스를 활성화한 경우
  - 불필요하게 과도한 권한을 부여한 경우
  - 보안 패치를 지연하여 알려진 취약점이 남아 있는 경우

## 1.3. 운영 환경 변화에 따른 보안 약화

- 시스템의 보안 상태는 처음 구축했을 때부터 계속 유지되는 것이 아니라 운영 과정에서 점차 약화될 수 있다.
- 다음과 같은 요인이 대표적이다.
  - 인력 교체
  - 시스템 및 서비스 추가
  - 업무상 예외 설정 증가
  - 사용자의 편의성을 위한 보안 설정 완화
  - 장기간 방치된 계정 및 서비스
- 따라서 정기적인 보안 점검을 통해 보안이 약화된 부분을 발견하고 통제 가능한 상태로 유지해야 한다.

# 2. 보안 장비와 OS 보안 점검의 관계

## 2.1. 보안 장비의 역할

- 방화벽, EDR, NAC 등의 보안 장비는 시스템 외부 또는 시스템과의 접점에서 네트워크 트래픽과 단말의 행위를 관찰한다.
- 각각의 주요 역할은 다음과 같다.

| 보안 장비 | 주요 관찰 영역 |
|---|---|
| 방화벽(Firewall) | 네트워크 경계의 트래픽 |
| EDR | 엔드포인트의 프로세스 및 행위 |
| NAC | 네트워크에 접속하는 단말 및 접근 상태 |

## 2.2. OS 내부의 보안 사각지대

- OS 내부에 존재하는 설정 문제는 보안 장비만으로 모두 확인하기 어렵다.
- 예를 들어 다음과 같은 문제가 존재할 수 있다.
  - 약한 비밀번호 정책
  - 불필요한 서비스 활성화
  - 과도한 사용자 권한
  - 불필요한 계정 존재
  - 잘못된 파일 및 디렉터리 권한
- 비밀번호 정책이 약하게 설정되어 있어도 방화벽은 해당 사실을 직접 판단하기 어렵다.
- 사용하지 않는 서비스가 활성화되어 있어도 실제 비정상 행위가 발생하기 전까지 EDR에서 명확하게 탐지하지 못할 수 있다.

## 2.3. 보안 장비와 OS 하드닝의 관계

- 보안 장비와 OS 하드닝은 서로 대체하는 관계가 아니라 **상호 보완하는 관계**이다.
- 비유하면 다음과 같이 이해할 수 있다.

> 보안 장비가 우산이라면 OS 하드닝은 비가 새지 않는 옷과 같다.

- 우산이 일시적으로 접히거나 제대로 작동하지 않는 상황에서도 시스템 자체의 보안 설정이 잘 되어 있다면 피해를 줄일 수 있다.
- 따라서 OS 보안 점검과 하드닝은 보안 장비의 한계를 보완하는 중요한 활동이다.

# 3. 침해사고 사례: Mirai 봇넷

## 3.1. Mirai 봇넷 개요

- **Mirai 봇넷**은 2016년에 알려진 악성코드로, Linux 기반 IoT 디바이스를 주요 대상으로 한다.
- Mirai는 인터넷에 노출된 IoT 장비를 탐색하고, 흔하게 사용되는 기본 계정 및 비밀번호 조합을 이용하여 장비에 침입하는 방식으로 확산되었다.
- 이후 감염된 장비를 봇넷으로 구성하여 대규모 DDoS 공격 등에 활용하였다.

## 3.2. 주요 공격 사례

- 2016년 9월에는 보안 전문 블로그 **KrebsOnSecurity**가 약 620Gbps 규모의 대규모 DDoS 공격을 받았다.
- 2016년 10월에는 DNS 서비스 제공업체 **Dyn**을 대상으로 대규모 DDoS 공격이 발생하였다.
- 이 공격의 영향으로 GitHub, Twitter, Netflix 등의 주요 서비스에서 접속 장애가 발생하였다.

## 3.3. Mirai가 주는 교훈

- Mirai 사례는 **기본 계정과 약한 인증 정보의 방치**가 실제 침해사고의 초기 침투 경로가 될 수 있음을 보여준다.
- 특히 IoT 장비처럼 다수의 시스템이 연결되어 있는 환경에서는 하나의 약한 시스템이 전체 인프라에 영향을 줄 수 있다.
- 따라서 다음과 같은 기본적인 보안 관리가 중요하다.
  - 기본 계정 및 비밀번호 변경
  - 강력한 인증 정책 적용
  - 불필요한 외부 접근 차단
  - 사용하지 않는 서비스 비활성화
  - 정기적인 보안 업데이트

# 4. 공격자의 침투 흐름 6단계

## 4.1. 공격 흐름 개요

- 공격자는 항상 새로운 공격 기법만 사용하는 것이 아니라 이미 효과가 검증된 공격 단계를 반복적으로 활용하는 경향이 있다.
- 공격 과정은 여러 단계가 연결된 하나의 사슬로 볼 수 있다.
- 사슬의 어느 한 고리라도 효과적으로 차단하면 전체 공격의 성공 가능성을 낮출 수 있다.

```text
초기 침투
    ↓
권한 상승
    ↓
측면 이동
    ↓
지속성 확보
    ↓
방어 회피
    ↓
영향 발생
```

## 4.2. 각 단계의 의미

| 단계 | 설명 |
|---|---|
| 초기 침투 | 공격자가 시스템 또는 네트워크에 처음 접근하는 단계이다. |
| 권한 상승 | 획득한 계정보다 높은 권한을 확보하는 단계이다. |
| 측면 이동 | 다른 시스템이나 계정으로 접근 범위를 확대하는 단계이다. |
| 지속성 | 시스템에 재접속할 수 있는 상태를 유지하는 단계이다. |
| 방어 회피 | 탐지 및 차단을 피하기 위해 보안 통제를 우회하는 단계이다. |
| 영향 발생 | 데이터 탈취, 서비스 중단 등의 실제 피해가 발생하는 단계이다. |

- Linux 보안 점검에서는 이러한 공격 흐름의 각 단계에서 악용될 수 있는 설정이나 관리상의 문제를 사전에 제거하는 것이 중요하다.

# 5. 보안 점검과 보안 하드닝의 차이

## 5.1. 보안 점검과 하드닝 비교

보안 점검과 보안 하드닝은 함께 수행되는 활동이지만 목적과 수행 방식에는 차이가 있다.

| 구분 | 보안 점검(Assessment) | 보안 하드닝(Hardening) |
|---|---|---|
| 비유 | 건강검진 | 치료 및 예방 |
| 목적 | 현재 보안 상태를 진단하고 취약점을 식별한다. | 보안 설정을 변경하고 불필요한 기능을 제거하여 보안을 강화한다. |
| 역할 | 문제를 발견하고 위험도를 평가한다. | 발견된 문제를 실제로 개선한다. |
| 시스템 변경 | 일반적으로 상태를 변경하지 않고 점검한다. | 설정 및 시스템 상태를 실제로 변경한다. |
| 산출물 | 취약점 목록, 위험도, 개선 권고 등이 포함된 보고서를 작성한다. | 적용된 설정과 강화된 시스템 상태를 확인한다. |

## 5.2. 점검과 하드닝의 차이

- **보안 점검**은 현재 시스템의 문제를 발견하고 위험을 평가하는 활동이다.
- **보안 하드닝**은 발견된 문제를 실제 설정 변경이나 기능 제거 등을 통해 개선하는 활동이다.
- 따라서 점검 결과를 바탕으로 하드닝을 수행하고, 이후 다시 점검하여 조치가 제대로 적용되었는지 확인하는 과정이 필요하다.

# 6. 점검과 하드닝의 지속적인 개선 사이클

보안 점검과 하드닝은 일회성 작업이 아니라 지속적인 개선 과정으로 운영하는 것이 중요하다.

```text
점검
 ↓
우선순위 수립
 ↓
하드닝
 ↓
재점검
 ↓
조치 결과 검증
 ↓
지속적인 개선
```

## 6.1. 단계별 내용

1. **점검**
   - 현재 시스템의 보안 상태를 파악하고 취약점을 식별한다.

2. **우선순위 수립**
   - 취약점의 위험도와 시스템에 미치는 영향을 검토하여 개선 순서를 결정한다.

3. **하드닝**
   - 실제 설정을 변경하고 불필요한 기능이나 서비스를 제거한다.

4. **재점검**
   - 하드닝 이후 문제가 제대로 해결되었는지 다시 확인한다.

5. **지속적인 개선**
   - 새로운 취약점이나 운영 환경의 변화를 반영하여 다시 점검하고 개선한다.

---

# 7. 점검·하드닝 운영 원칙

## 7.1. 점검과 하드닝의 상호보완

- 하드닝이 없는 점검은 문제를 발견하는 것에 그치기 쉽다.
- 반대로 점검이 없는 하드닝은 실제 위험을 고려하지 않은 설정 변경이 될 수 있다.
- 따라서 **점검 → 개선 → 재점검**의 순환 구조를 유지해야 한다.

## 7.2. 위험 기반 접근

- 모든 보안 항목을 한 번에 적용하기 어려운 경우 위험도가 높은 항목부터 단계적으로 개선해야 한다.
- 우선순위를 정할 때 다음 요소를 고려할 수 있다.
  - 취약점의 심각도
  - 시스템의 중요도
  - 예상되는 피해 규모
  - 외부 노출 여부
  - 공격 가능성

## 7.3. 대체 통제

- 즉시 설정을 변경하기 어려운 경우에는 다른 보안 통제를 적용하여 위험을 먼저 낮출 수 있다.
- 예를 들어 다음과 같은 방법을 사용할 수 있다.
  - 접근 가능한 네트워크 구간 제한
  - 방화벽 정책 강화
  - 관리자 접근 통제
  - 모니터링 강화
  - 로그 수집 및 분석 강화

- 결국 보안 운영은 모든 문제를 한 번에 해결하는 것이 아니라 **위험이 큰 지점부터 지속적으로 줄여나가는 과정**이다.

# 8. Linux 시스템 보안 점검 개요

## 8.1. KISA 주요정보통신기반시설 가이드

- 한국인터넷진흥원(KISA)에서는 주요정보통신기반시설의 보안 취약점을 점검하기 위한 가이드를 제공한다.
- 정식 명칭은「주요정보통신기반시설 기술적 취약점 분석·평가 방법 상세가이드」이다.
- 문서의 명칭이 길기 때문에 일반적으로 **KISA 가이드**라고 부르기도 한다.
- 공공, 금융, 통신 등 다양한 기관의 보안 점검에서 참고 기준으로 활용된다.

## 8.2. Unix 서버 분야 점검 항목

- 가이드에서는 Unix 계열 서버를 대상으로 다양한 보안 점검 항목을 제공한다.
- 대표적인 분류는 다음과 같다.

| 분류 | 주요 점검 내용 |
|---|---|
| 계정 관리 | 계정, 비밀번호, 권한 등의 관리 상태를 점검한다. |
| 파일 및 디렉터리 관리 | 중요 파일과 디렉터리의 권한 및 소유자를 점검한다. |
| 서비스 관리 | 불필요한 서비스와 보안 설정을 점검한다. |
| 패치 관리 | 운영체제 및 소프트웨어의 보안 업데이트 상태를 점검한다. |
| 로그 관리 | 시스템 및 보안 로그의 설정과 관리 상태를 점검한다. |

- 원문 기준으로 Unix 서버 분야는 **67개 점검 항목**을 위와 같은 5개 분류로 구성한다.

# 9. KISA 가이드 확보 및 활용

## 9.1. KISA 가이드 확보 방법

- KISA의 보호나라 홈페이지에서 관련 가이드를 확인하고 다운로드할 수 있다.
- 공식 가이드를 활용하면 임의로 점검 기준을 만드는 것보다 체계적인 보안 점검을 수행할 수 있다.

## 9.2. 활용 범위

- 가이드에는 항목별로 다음과 같은 내용이 정리되어 있다.
  - 점검 내용
  - 점검 기준
  - 취약점 판단 기준
  - 조치 방법
- 따라서 기관이나 기업의 정기적인 보안 점검뿐만 아니라 Linux 보안 학습 및 자가 점검에도 활용할 수 있다.

## 9.3. 학습 시 활용 방법

- 각 점검 항목을 실제 Linux 시스템에서 확인하면서 다음과 같은 방식으로 학습할 수 있다.

```text
점검 기준 확인
    ↓
현재 시스템 설정 확인
    ↓
취약 여부 판단
    ↓
문제 원인 분석
    ↓
개선 방법 확인
    ↓
하드닝 적용
    ↓
재점검
```

- 단순히 점검 결과를 `양호/취약`으로 판단하는 것보다 **왜 해당 설정이 보안상 중요한지**를 이해하는 것이 중요하다.

# 10. 핵심내용 (Summary)

1. **Linux 보안 점검의 필요성**
   - Linux는 서버, 클라우드, IoT 등 다양한 환경에서 사용되기 때문에 보안 점검의 중요성이 높다.

2. **설정과 관리의 중요성**
   - 기본 비밀번호, 불필요한 서비스, 과도한 권한, 패치 지연과 같은 관리상의 문제가 침해사고의 원인이 될 수 있다.

3. **보안 장비와 OS 보안의 관계**
   - 방화벽, EDR, NAC 등의 보안 장비만으로 OS 내부의 모든 보안 문제를 해결할 수 없다.
   - OS 자체의 계정, 권한, 서비스, 파일 시스템 등의 보안 설정을 함께 관리해야 한다.

4. **Mirai 봇넷의 교훈**
   - 기본 계정과 약한 인증 정보의 방치는 실제 공격의 초기 침투 경로가 될 수 있다.
   - IoT와 Linux 기반 시스템에서 기본적인 보안 설정을 반드시 관리해야 한다.

5. **공격 흐름과 보안 점검**
   - 공격은 초기 침투부터 권한 상승, 측면 이동, 지속성, 방어 회피, 영향 발생 등의 단계로 이어질 수 있다.
   - 각 단계에서 공격자가 악용할 수 있는 약점을 사전에 제거하는 것이 중요하다.

6. **보안 점검과 하드닝의 차이**
   - 보안 점검은 문제를 **발견하고 평가**하는 활동이고, 하드닝은 문제를 **실제로 개선**하는 활동이다.

7. **지속적인 보안 관리**
   - `점검 → 우선순위 수립 → 하드닝 → 재점검`의 사이클을 반복하여 시스템의 보안 수준을 지속적으로 개선해야 한다.

8. **위험 기반 접근**
   - 모든 보안 문제를 동시에 해결하기 어렵다면 위험도와 영향도가 높은 항목부터 우선적으로 개선해야 한다.
   - 즉시 개선하기 어려운 경우에는 접근 제한이나 모니터링 강화 등의 대체 통제를 적용할 수 있다.

9. **KISA 가이드 활용**
   - 「주요정보통신기반시설 기술적 취약점 분석·평가 방법 상세가이드」를 활용하면 Linux 및 Unix 서버의 보안 상태를 체계적으로 점검할 수 있다.
